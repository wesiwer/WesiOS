# WesiOS — Product Discovery: 50 вопросов о целевой корпоративной ОС

**Статус:** живое нормативное дополнение к ТЗ

## Зафиксированные ответы

### 1/50. Что такое WesiOS в конечном виде?

**Ответ:** B — полноценная корпоративная ОС.

**Нормативное следствие:**

- каждый сотрудник работает в WesiOS ежедневно;
- WesiOS не является только CEO-dashboard или вспомогательной финансовой панелью;
- основные рабочие процессы сотрудников должны быть доступны внутри WesiOS: задачи, CRM, проекты, коммуникации, календарь, документы, персональные и разрешённые корпоративные данные;
- архитектура должна проектироваться как multi-user corporate workspace, а не single-owner utility.

### 2/50. Насколько разным должен быть интерфейс для разных ролей?

**Ответ:** B — интерфейс существенно адаптируется под роль.

**Нормативное следствие:**

- недостаточно просто скрывать недоступные пункты меню;
- состав главного экрана, основные модули, быстрые действия, показатели и рабочие сценарии должны зависеть от активной роли;
- программист, сотрудник продаж, руководитель и CEO получают разные рабочие пространства.

### 3/50. Как устроена главная страница?

**Ответ:** B — главная страница зависит от роли.

**Нормативное следствие:**

Примеры целевого поведения:

- разработчик: задачи, GitHub, проекты, дедлайны;
- продажи: CRM, сделки, клиенты, план;
- руководитель: команда, задачи подразделения, финансы, риски;
- CEO: дерево компаний, консолидированные финансы, подразделения, ключевые риски и управленческие показатели.

Главная не должна быть одной универсальной панелью для всех.

### 4/50. Может ли сотрудник иметь несколько ролей?

**Ответ:** C — да, с явным переключением рабочего режима.

**Нормативное следствие:**

- один Employee может иметь несколько RoleAssignment;
- пользователь явно выбирает активный рабочий режим;
- пример: `Руководитель Studio A` / `Разработчик Studio A` / `Project X`;
- активный режим должен менять интерфейс, доступные действия и рабочий контекст;
- роль не должна быть единственным неизменяемым полем Employee.

### 5/50. Суммируются ли права нескольких ролей?

**Ответ:** B — нет. Активная роль является настоящим security-context.

**Нормативное следствие:**

- права не суммируются автоматически между всеми назначенными ролями;
- в режиме `Разработчик` пользователь не получает административные/финансовые полномочия роли `Руководитель`;
- для действия, требующего другой роли, пользователь должен явно переключить active role;
- authorization должна вычисляться минимум как `user + activeRoleAssignment + organization scope + permission`, а не просто как union всех grants пользователя;
- смена active role должна быть auditable для чувствительных действий;
- UI security-context и service/domain enforcement должны использовать один и тот же active role.

### 6/50. Как роль связана с организацией?

**Ответ:** A — каждая роль жёстко связана с конкретной организацией или её разрешённым subtree.

**Нормативное следствие:**

- RoleAssignment хранит organizationId и допустимый scope;
- выбор `Руководитель Studio A` автоматически выбирает соответствующий organization context;
- пользователь не выбирает произвольную комбинацию роли и организации, если такой RoleAssignment ему не назначен;
- один человек может иметь разные роли в разных организациях;
- пример: `Developer@StudioA` и `Developer@StudioB` — два разных рабочих/security-контекста;
- OrganizationContext и ActiveRoleContext должны переключаться согласованно и атомарно;
- все Tasks/CRM/Treasury/Analytics/Horizon/Contacts и будущие модули должны учитывать активный RoleAssignment.

### 7/50. Кто создаёт и назначает роли?

**Ответ:** D — комбинированная модель управления.

**Нормативное следствие:**

- CEO/root owner может создавать и назначать любые допустимые роли;
- руководитель организации может назначать роли только в пределах своей ветки и не выше собственных полномочий;
- HR/admin получает отдельные делегированные права на управление сотрудниками и RoleAssignment;
- нельзя выдавать permission, scope или роль, которых нет у назначающего субъекта, если специальная системная политика явно не разрешает это;
- все назначения, изменения и отзывы ролей должны попадать в аудит.

### 8/50. Откуда берутся роли?

**Ответ:** C — системные шаблоны + пользовательские роли.

**Нормативное следствие:**

- WesiOS содержит стандартный каталог шаблонов ролей;
- CEO и уполномоченные руководители могут создавать собственные роли;
- системный шаблон можно копировать и адаптировать под конкретную организацию;
- роль должна описывать не только permissions, но и целевое рабочее пространство/UX активного контекста.

### 9/50. Что происходит при изменении шаблона роли?

**Ответ:** B — назначение является независимой копией.

**Нормативное следствие:**

- шаблон используется как стартовая конфигурация;
- при назначении сотруднику создаётся независимая конфигурация RoleAssignment;
- дальнейшие изменения исходного шаблона не должны автоматически и молча менять права уже работающих сотрудников;
- связь с source template может сохраняться для сравнения и аудита, но не как live-binding permissions.

### 10/50. Можно ли индивидуально менять права конкретному сотруднику внутри роли?

**Ответ:** D — да, с обязательной прозрачностью отклонений.

**Нормативное следствие:**

- permissions конкретного RoleAssignment можно индивидуально включать/отключать в пределах полномочий назначающего;
- WesiOS показывает diff относительно исходного шаблона;
- для каждого изменения сохраняются автор, время, причина/контекст и история;
- должно быть возможно понять источник каждого эффективного permission;
- индивидуальное изменение не должно создавать скрытый неаудируемый grant.

### 11/50. Что происходит при увольнении или временном отстранении сотрудника?

**Ответ:** D — полноценный lifecycle сотрудника.

**Нормативное следствие:**

- поддерживаются как минимум состояния `active`, `vacation`, `on_leave`, `suspended`, `terminated` с возможностью расширения;
- каждый статус имеет собственную политику доступа;
- увольнение не удаляет историю сотрудника;
- offboarding завершает активные сессии, отзывает роли/ключи/интеграционные доступы и предлагает передачу задач, клиентов, проектов и ответственности;
- деактивированного сотрудника можно реактивировать, если его статус и политика это допускают;
- история задач, сделок, операций, комментариев, KPI и аудита сохраняется с исходным employeeId.

### 12/50. Насколько сотрудникам видна структура всей Wesi?

**Ответ:** C — базовая оргструктура прозрачна для всех сотрудников.

**Нормативное следствие:**

- все активные сотрудники могут видеть общее дерево Wesi;
- базовый профиль сотрудника включает имя, должность, организацию и рабочие контакты;
- базовая оргвидимость не даёт доступа к чувствительным данным;
- задачи, KPI, зарплаты, финансы, сделки, аудиты и прочие закрытые данные продолжают проверяться через active security-context и permissions.

### 13/50. Как работает видимость задач?

**Ответ:** D — role/scope access + собственный уровень видимости задачи.

**Нормативное следствие:**

- сотрудник видит свои задачи и задачи доступных ему проектов;
- руководитель видит задачи разрешённой org/subtree согласно активной роли;
- Task получает visibility scope минимум: `private`, `project`, `organization`, `subtree`, `company`;
- visibility scope не может расширить доступ сверх effective permissions активного RoleAssignment;
- service/domain слой обязан проверять task visibility и security-context, а не полагаться только на UI-фильтры.

### 14/50. Насколько полноценной должна быть система задач?

**Ответ:** D — Tasks является универсальной рабочей сущностью WesiOS.

**Нормативное следствие:**

- Task поддерживает подзадачи, зависимости, приоритеты, метки, этапы/статусы, комментарии, вложения, наблюдателей, упоминания и полную историю изменений;
- задача может иметь нескольких участников/исполнителей согласно модели доступа;
- Task может быть связан с Project, CRM Client/Deal, GitHub Issue/PR, Document, Organization, финансовым запросом и другими доменными сущностями;
- из карточки задачи должен быть доступен связанный рабочий контекст;
- автоматизации и AI-модули могут создавать/изменять задачи только в рамках разрешённого security-context и с аудитом;
- Tasks должен стать общей координационной сущностью для рабочих процессов разных модулей, а не изолированным списком todo.

## Архитектурные требования, выявленные вопросами 4–14

### RoleAssignment

```text
RoleAssignment
- id
- employeeId
- sourceTemplateId?
- roleName / roleType
- organizationId
- scope: only | subtree
- permissions
- permissionOverrides / diffFromTemplate
- workspaceProfile
- status
- createdAt
- updatedAt
- createdBy
```

### ActiveWorkContext

```text
ActiveWorkContext
- employeeId
- roleAssignmentId
- organizationId
- organizationScope
```

### EmployeeLifecycle

```text
EmployeeStatus
- active
- vacation
- on_leave
- suspended
- terminated
- extensible future statuses
```

### Authorization pipeline

```text
кто вошёл
→ какой EmployeeStatus действует сейчас
→ какую назначенную роль пользователь активировал
→ к какой организации/ветке относится роль
→ какие permissions разрешены именно этой ролью
→ какие object-level visibility rules действуют
→ какие данные и действия доступны в текущем модуле
```

### Task visibility

```text
TaskVisibility
- private
- project
- organization
- subtree
- company
```

Object-level visibility никогда не расширяет права сверх active RoleAssignment.
