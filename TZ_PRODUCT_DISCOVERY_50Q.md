## Зафиксированные ответы

### 1/50. Что такое WesiOS в конечном виде?

**Ответ:** B — полноценная корпоративная ОС.

**Нормативное следствие:**

- каждый сотрудник работает в WesiOS ежедневно;
- WesiOS не является только CEO-dashboard или вспомогательной финансовой панелью;
- основные рабочие процессы сотрудников должны быть доступны внутри WesiOS: задачи, CRM, проекты, коммуникации, календарь, документы, персональные и разрешённые корпоративные данные;
- архитектура должна проектироваться как multi-user corporate workspace, а не single-owner utility.

### 2/50. Насколько разным должен быть интерфейс для разных ролей?

**Ответ:** B — интерфейс существенно адаптируется под роль.

**Нормативное следствие:**

- недостаточно просто скрывать недоступные пункты меню;
- состав главного экрана, основные модули, быстрые действия, показатели и рабочие сценарии должны зависеть от активной роли;
- программист, сотрудник продаж, руководитель и CEO получают разные рабочие пространства.

### 3/50. Как устроена главная страница?

**Ответ:** B — главная страница зависит от роли.

**Нормативное следствие:**

Примеры целевого поведения:

- разработчик: задачи, GitHub, проекты, дедлайны;
- продажи: CRM, сделки, клиенты, план;
- руководитель: команда, задачи подразделения, финансы, риски;
- CEO: дерево компаний, консолидированные финансы, подразделения, ключевые риски и управленческие показатели.

Главная не должна быть одной универсальной панелью для всех.

### 4/50. Может ли сотрудник иметь несколько ролей?

**Ответ:** C — да, с явным переключением рабочего режима.

**Нормативное следствие:**

- один Employee может иметь несколько RoleAssignment;
- пользователь явно выбирает активный рабочий режим;
- пример: `Руководитель Studio A` / `Разработчик Studio A` / `Project X`;
- активный режим должен менять интерфейс, доступные действия и рабочий контекст;
- роль не должна быть единственным неизменяемым полем Employee.

### 5/50. Суммируются ли права нескольких ролей?

**Ответ:** B — нет. Активная роль является настоящим security-context.

**Нормативное следствие:**

- права не суммируются автоматически между всеми назначенными ролями;
- в режиме `Разработчик` пользователь не получает административные/финансовые полномочия роли `Руководитель`;
- для действия, требующего другой роли, пользователь должен явно переключить active role;
- authorization должна вычисляться минимум как `user + activeRoleAssignment + organization scope + permission`, а не просто как union всех grants пользователя;
- смена active role должна быть auditable для чувствительных действий;
- UI security-context и service/domain enforcement должны использовать один и тот же active role.

### 6/50. Как роль связана с организацией?

**Ответ:** A — каждая роль жёстко связана с конкретной организацией или её разрешённым subtree.

**Нормативное следствие:**

- RoleAssignment хранит organizationId и допустимый scope;
- выбор `Руководитель Studio A` автоматически выбирает соответствующий organization context;
- пользователь не выбирает произвольную комбинацию роли и организации, если такой RoleAssignment ему не назначен;
- один человек может иметь разные роли в разных организациях;
- пример: `Developer@StudioA` и `Developer@StudioB` — два разных рабочих/security-контекста;
- OrganizationContext и ActiveRoleContext должны переключаться согласованно и атомарно;
- все Tasks/CRM/Treasury/Analytics/Horizon/Contacts и будущие модули должны учитывать активный RoleAssignment.

## Архитектурное требование, выявленное вопросами 4–6

В существующую модель необходимо добавить отдельную сущность наподобие:

```text
RoleAssignment
- id
- employeeId
- roleId / roleType
- organizationId
- scope: only | subtree
- permissions / policy reference
- status: active | suspended | archived
- createdAt
- updatedAt
- createdBy
```

И runtime-контекст:

```text
ActiveWorkContext
- employeeId
- roleAssignmentId
- organizationId
- organizationScope
```

Основной authorization pipeline должен стать:

```text
кто вошёл
→ какую назначенную роль он сейчас активировал
→ к какой организации/ветке относится эта роль
→ какие права разрешены именно этой ролью
→ какие данные и действия доступны в текущем модуле
```

Это требование является обязательным для последующей доработки и имеет приоритет над моделью, где права пользователя просто суммируются.
