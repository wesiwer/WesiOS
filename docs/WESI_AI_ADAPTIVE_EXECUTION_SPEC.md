# Wesi AI — Adaptive Execution & Resource Budget Specification

**Статус:** обязательное расширение `docs/WESI_AI_MASTER_SPEC.md` и Persona Co-Agent ТЗ.

## Главный принцип

Мощность агентной системы включается **только по необходимости**. Нельзя запускать полный Orchestrator, Зейна, Нирвану, несколько субагентов, браузер, build toolchain и media runtime для простой задачи.

Wesi AI обязана выбирать **минимальный достаточный execution path** для конкретного запроса.

## Уровни исполнения

### L0 — Chat
Обычный вопрос/диалог.
- только выбранная persona/LLM;
- без субагентов;
- без Local Runtime;
- без тяжёлых tools.

### L1 — Simple Action
Небольшая правка/операция: переименовать кнопку, поправить один файл, конвертировать простой документ.
- один ведущий Persona Agent;
- минимально необходимые tools;
- одна быстрая проверка результата;
- второй Persona Agent не вызывается без пользы.

### L2 — Assisted Task
Задача средней сложности.
- Lead Persona;
- при необходимости один Co-Agent либо один узкий subagent;
- targeted tests/validation;
- ограниченный workspace.

### L3 — Complex Agent Task
Сложная разработка/исследование/дизайн.
- Lead Persona;
- Co-Agent по специализации;
- необходимые динамические субагенты;
- self-debug loop;
- полноценные tests/build/review.

### L4 — Heavy Runtime / Media
Сборки, браузерные интеграционные тесты, тяжёлый рендер, локальная AI-генерация.
- только подходящий desktop/remote worker;
- Resource Scheduler и очередь обязательны;
- тяжёлые операции не запускаются параллельно без достаточного resource budget.

## Запрет over-orchestration

Пример: запрос «переименуй кнопку» не должен автоматически создавать Нирвану + Зейна + QA + Flutter specialist и запускать полный release build. Достаточно Lead Persona, изменения файла и минимальной релевантной проверки.

Co-Agent и subagents вызываются только если ожидаемая польза превышает стоимость по времени, API-вызовам и ресурсам устройства.

## Resource Budget

Перед локальной тяжёлой операцией Scheduler оценивает:
- CPU load/cores;
- доступную RAM;
- GPU и свободную VRAM;
- свободный диск;
- температуру/энергетический режим, если платформа предоставляет безопасный API;
- уже выполняющиеся jobs;
- прогнозируемый класс нагрузки новой задачи.

Нужны лимиты параллелизма. На устройстве среднего класса нельзя одновременно запускать несколько Gradle/Flutter builds, Chromium integration tests и локальную video generation, если это приведёт к memory pressure/зависанию.

При нехватке ресурсов операция ставится в очередь, переносится на другой worker или возвращает понятный blocker.

## Progressive Escalation

Система начинает с самого дешёвого разумного уровня и повышает уровень только при необходимости.

Пример:
`simple edit -> targeted validation failed -> Debug subagent -> broader tests -> build`, а не `full multi-agent build` с первой секунды.

Если задача оказалась проще ожидаемого, система не обязана использовать уже доступные тяжёлые capabilities.

## API Cost Budget

Параллельность субагентов учитывает не только железо, но и стоимость/лимиты внешних AI API. Нельзя создавать десятки LLM-вызовов, если один Lead Agent способен надёжно решить задачу.

Для каждого job должны учитываться разумные лимиты:
- max active subagents;
- max repair iterations;
- max wall-clock duration;
- API/provider rate limits;
- token/context budget.

Достижение лимита не означает скрытую остановку: Lead Persona сообщает объективный blocker и доступные варианты продолжения.

## Пользовательский опыт

Пользователь не обязан вручную выбирать количество агентов для обычной работы. Adaptive Execution выбирает уровень автоматически.

При тяжёлой задаче интерфейс может показать, что потребуется desktop worker/дополнительный Runtime Pack/значительное время или ресурсы.

Для удалённого desktop worker действует прежнее обязательное правило: если задача требует ПК, а WesiOS на нём недоступен, мобильное приложение сообщает, что WesiOS на привязанном компьютере необходимо открыть и оставить доступным.

## Реалистичная поэтапная готовность

Wesi AI не должна считаться надёжной только из-за наличия архитектуры. Реализация идёт слоями и каждый слой стабилизируется тестами до расширения автономности:
1. стабильный текстовый Persona Chat;
2. attachments и tools;
3. controlled local execution;
4. self-debug;
5. Remote Worker;
6. Persona Co-Agent handoff;
7. dynamic subagents;
8. сложные media/runtime pipelines.

Нельзя включать новый уровень автономности в production, если предыдущий уровень не имеет достаточных тестов, observability и безопасного rollback.

## Критерий

Целевая система должна быть мощной на сложных задачах и дешёвой на простых. Правило по умолчанию:

**Использовать минимальное количество моделей, агентов, инструментов и вычислительных ресурсов, достаточное для надёжного выполнения текущей задачи.**
