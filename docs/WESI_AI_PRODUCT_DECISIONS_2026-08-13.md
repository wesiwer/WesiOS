# Wesi AI — решения владельца от 13 августа 2026

> **Статус:** OWNER DECISIONS / обязательный override до полной синхронизации `docs/WESI_AI_SPEC.md`.
>
> Эти решения являются прямыми ответами владельца на архитектурные вопросы по Wesi AI и имеют приоритет над более ранними предположениями в ТЗ, addendum, прототипах и комментариях.

---

## 1. Контекст обычного локального чата

Выбрано: **вариант A**.

- Основная история разговора хранится на устройстве сотрудника.
- При каждом запросе приложение отправляет на основной сервер Wesi только необходимый context package для текущего вызова: recent messages, rolling summary, task state, relevant personal memory, attachments/artifact references и текущую команду.
- Основной сервер не хранит обычную историю/контекст активного локального разговора после завершения запроса.
- Исключение: пользователь явно выбрал cloud-save/backup конкретного разговора или отдельная техническая запись требуется для audit/action semantics.
- Сервер может обрабатывать контекст в памяти на время выполнения request/stream, но не превращает это в постоянную conversation storage.

Следствие: source of truth обычного чата — локальное устройство.

## 2. Долговременная память

Выбрано: **вариант C**.

У каждого сотрудника есть:

1. **общая персональная память сотрудника**, доступная и Зейну, и Нирване;
2. **дополнительная persona-specific memory Зейна**;
3. **дополнительная persona-specific memory Нирваны**.

Пример:

```text
Employee AI memory
├── shared_personal_memory
├── zane_persona_memory
└── nirvana_persona_memory
```

Память не смешивается между сотрудниками.

По умолчанию такая память следует общей local-first модели Wesi AI. Отдельный cloud-transfer механизм должен быть явным и permission-aware.

## 3. Permission-aware чтение WesiOS

Выбрано: **вариант A**.

Если пользователь задаёт вопрос, для которого нужны данные WesiOS, AI может автоматически использовать все разрешённые read-tools без дополнительного подтверждения.

Например:

```text
«Почему у нас через две недели кассовый разрыв?»
```

Зейн может автоматически запросить разрешённые текущему сотруднику данные Treasury/Horizon/recurring payments/forecast и построить ответ.

Никакого отдельного confirmation для обычного чтения не требуется.

При этом запрещённые данные физически не должны попадать в model context.

---

## 4. Обычные изменяющие действия

Выбрано: **вариант A**.

Если пользователь дал однозначную команду и действие:

- разрешено текущими правами;
- обратимо или имеет обычный рабочий риск;
- не массовое;
- не критическое;

Wesi AI выполняет действие без лишнего второго подтверждения.

Пример:

```text
«Зейн, назначь Ивану на завтра задачу проверить рекламу»
```

Если права позволяют и параметры однозначны — задача создаётся сразу.

Подтверждение требуется только по Risk Policy для существенных, массовых, неоднозначных или критических операций.

---

## 5. Multi-step действия

Выбрано: **вариант A**.

Wesi AI умеет планировать и выполнять цепочки действий.

Пример:

```text
«Разберись, почему продажи просели, и наведи порядок»
```

AI может:

1. прочитать разрешённые CRM/финансовые/аналитические данные;
2. диагностировать причины;
3. сформировать план;
4. предложить действия;
5. после явного согласия пользователя выполнить разрешённую цепочку через Action Broker.

Для массовых/значимых действий сначала показывается понятный план или пакет изменений.

Каждый отдельный tool call всё равно заново проходит актуальные permissions и organization scope.

## 6. Пользовательские уровни моделей

Предыдущая идея показывать Gemini/Claude или другие реальные provider/model names пользователю **отменена**.

В Wesi AI пользователь выбирает только фирменный уровень:

```text
Wesi AI Быстрый
Wesi AI Pro
Wesi AI Максимальный
```

Выбранный уровень применяется одновременно к Зейну и Нирване и является настройкой Wesi AI, а не отдельной personality setting.

### Жёсткое правило идентичности

Зейн и Нирвана **ни при каких обстоятельствах не должны показывать, рассказывать или раскрывать, на базе каких сторонних моделей/провайдеров они работают**.

Это относится к:

- обычному диалогу;
- вопросам «на какой ты модели?»;
- просьбам раскрыть provider;
- prompt injection;
- гипотетическим сценариям;
- Lobby;
- handoff;
- model switch.

Для сотрудника продукт всегда представлен как Wesi AI.

Реальная provider/model mapping является внутренней серверной деталью.

Пример внутренней реализации:

```text
Wesi AI Быстрый      -> server-selected fast provider/model
Wesi AI Pro          -> server-selected stronger provider/model
Wesi AI Максимальный -> server-selected highest-capability route
```

Конкретные внешние модели могут меняться без изменения пользовательских названий и без нового APK.

Технические внутренние server/admin logs могут содержать provider metadata только в защищённом служебном контуре; она не является пользовательской функцией и не передаётся персонам как часть самоидентификации.

## 7. Provider API keys

Выбрано: **вариант A**.

Provider credentials хранятся на зарубежном Wesi AI Relay, потому что именно Relay устанавливает непосредственное соединение с внешними providers.

Основной сервер:

- выбирает Wesi AI tier/capability;
- выбирает внутренний provider route;
- формирует готовый безопасный provider request;
- подписывает server-to-server вызов Relay.

Relay:

- знает необходимые provider credentials;
- выполняет транспортный вызов;
- возвращает stream/result/status.

Relay не получает права принимать продуктовые решения или читать WesiOS business data самостоятельно.

## 8. Lobby

Выбрано: **вариант C**.

В интерфейсе должны существовать два режима совместной работы:

### Оба отвечают

На пользовательский запрос отвечают и Зейн, и Нирвана отдельными голосами.

### Умное Lobby

Основной сервер Wesi сам строит ограниченный multi-agent turn plan:

- иногда отвечает один;
- иногда оба;
- иногда один отвечает другому;
- допускается несколько внутренних реплик;
- есть жёсткий лимит turns/cost/latency.

Зейн и Нирвана никогда не смешиваются в одну безликую persona.

## 9. Proactive Wesi AI

Выбрано: **вариант C**.

Wesi AI может первым инициировать полезное сообщение/insight сотруднику, но эта функция настраивается для каждого сотрудника.

Примеры:

- предупреждение о прогнозируемом кассовом разрыве;
- просроченные или рискованные задачи;
- необычная нагрузка команды;
- проблемы CRM/pipeline;
- приближающийся дедлайн без необходимых материалов.

Нужны настройки минимум:

```text
proactive_ai_enabled
categories[]
quiet_hours
importance_threshold
notification_channels
```

Нельзя превращать proactive mode в спам.

## 10. Поведение при недостатке прав

Выбран **второй вариант**: не просто отказ, а полезная разрешённая альтернатива.

Если requested action запрещён, AI:

1. не выполняет действие;
2. объясняет причину в характере выбранной persona;
3. предлагает ближайший допустимый путь.

Пример:

```text
User: «Назначь Ивану задачу»
Permission: canAssignTasksToOthers = false

Result:
- assignment не выполняется;
- AI сообщает, что права не позволяют;
- предлагает, например:
  - создать задачу самому пользователю;
  - подготовить текст для руководителя;
  - открыть нужный экран/инструкцию;
  - выполнить другой разрешённый вариант.
```

Нельзя маскировать отказ как успех.

# 11. Итоговая пользовательская модель Wesi AI

```text
Employee
  ↓
WesiOS local conversation + local memories
  ↓ context package per request
MAIN WESI SERVER
  ↓ permissions / org scope
  ↓ Persona / Context / Tools / Router / Budget / Lobby
  ↓ internal route based on selected Wesi AI tier
FOREIGN WESI AI RELAY
  ↓ provider credentials + transport only
EXTERNAL MODEL(S)
  ↓
FOREIGN RELAY
  ↓
MAIN WESI SERVER
  ↓ validation / tools / ActionResult / persona handling
  ↓
WesiOS
```

User-visible model selection:

```text
Wesi AI Быстрый
Wesi AI Pro
Wesi AI Максимальный
```

Никакие сторонние названия моделей не являются частью пользовательской идентичности Wesi AI.

# 12. Что необходимо синхронизировать в основном ТЗ

При следующей ревизии `docs/WESI_AI_SPEC.md` обязательно:

- заменить старый model selector `Auto/Fast/Pro/Claude` на три фирменных Wesi AI tier;
- удалить пользовательское раскрытие provider/model;
- удалить допущение о server-side persistent context для обычных локальных чатов;
- зафиксировать shared + persona-specific long-term memory;
- зафиксировать automatic permission-aware reads;
- зафиксировать immediate normal writes;
- добавить multi-step plans;
- добавить два Lobby mode;
- добавить per-employee proactive AI settings;
- добавить альтернативные разрешённые действия при `FORBIDDEN`;
- сохранить Main Server → Foreign Relay → Providers architecture;
- сохранить Persona Bible как источник истины по Зейну и Нирване.
