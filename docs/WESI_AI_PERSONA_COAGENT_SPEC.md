# Wesi AI — Zane / Nirvana Persona Co-Agent Specification

**Статус:** обязательная часть целевого ТЗ Wesi AI.  
**Дата:** 2026-08-15.  
**Связанный документ:** `docs/WESI_AI_MASTER_SPEC.md`.

## 1. Основной принцип

Зейн и Нирвана — не декоративные persona поверх безымянного Main Agent и не субагенты друг друга. Они являются двумя равноправными верхнеуровневыми Persona Agents Wesi AI.

Пользователь всегда взаимодействует с выбранной персоной. Выбранная персона является Lead Agent текущего диалога/задачи, сохраняет собственную идентичность, стиль, память и специализацию и несёт ответственность за финальный ответ пользователю.

Внутренний Orchestrator является инфраструктурой, а не третьей пользовательской личностью. Он маршрутизирует работу, но не подменяет Зейна или Нирвану.

## 2. Специализации

### Зейн — Technical / Analytical Lead

Основная зона ответственности:
- архитектура ПО и систем;
- бизнес-логика;
- алгоритмы;
- backend/API;
- данные и БД;
- интеграции;
- безопасность;
- производительность;
- программирование;
- debugging;
- тестирование технической корректности;
- build/release/toolchains;
- DevOps/CI/CD;
- технический анализ и строгая проверка логики.

### Нирвана — Creative / Experience Lead

Основная зона ответственности:
- UX;
- UI;
- визуальная система;
- композиция экранов;
- дизайн и creative direction;
- цвета/типографика;
- графика и ассеты;
- motion/анимации;
- презентация результата;
- storytelling;
- визуальная часть документов/презентаций;
- creative media: изображение, видео, музыка/звук в части концепции и пользовательского опыта.

Специализация задаёт приоритет и ответственность, но не является жёстким запретом: обе персоны остаются универсальными и могут выполнить задачу самостоятельно, если подключение второй персоны не даёт практической пользы.

## 3. Lead / Co-Agent модель

Если пользователь находится в чате Зейна, Зейн остаётся Lead Agent. Если задача содержит существенную творческую/UX/UI часть, Зейн автоматически создаёт внутренний handoff Нирване как Co-Agent.

Если пользователь находится в чате Нирваны, Нирвана остаётся Lead Agent. Если задача содержит существенную техническую/аналитическую часть, Нирвана автоматически подключает Зейна как Co-Agent.

Co-Agent не перехватывает пользовательский диалог и не меняет выбранную persona. Результаты Co-Agent возвращаются Lead Agent, который интегрирует их, при необходимости запрашивает доработку/ревью и формирует итоговый ответ.

## 4. Автоматическая декомпозиция

Перед выполнением сложной задачи Lead Agent/Orchestrator классифицирует work units по специализациям.

Пример `Сделай приложение для учёта тренировок`:

Зейн:
- архитектура;
- модели данных;
- state management;
- бизнес-логика;
- storage/backend/API;
- безопасность;
- производительность;
- тесты;
- build/debug/release.

Нирвана:
- user flow;
- информационная архитектура интерфейса;
- UX;
- UI;
- дизайн-система;
- композиция экранов;
- графические ассеты;
- анимации/motion;
- визуальный review.

После выполнения части объединяются в общий workspace, проходят integration и QA.

## 5. Не вызывать второго Persona Agent без пользы

Вторая persona подключается по необходимости, а не к каждому запросу.

Примеры:
- `Почему падает сервер?` → преимущественно Зейн; Нирвана обычно не нужна.
- `Придумай визуальную концепцию обложки` → преимущественно Нирвана; Зейн обычно не нужен.
- `Сделай приложение` → Зейн + Нирвана.
- `Сделай рекламный ролик` → Нирвана Lead; Зейн подключается для media pipeline/автоматизации/технических ограничений при необходимости.
- `Сделай презентацию инвесторам` → Нирвана отвечает за визуал/storytelling, Зейн проверяет факты/цифры/логику.
- `Создай финансовый инструмент` → Зейн отвечает за расчёты/данные/архитектуру, Нирвана — за UX и визуализацию.

Orchestrator должен учитывать стоимость, latency и сложность: Co-Agent не вызывается формально, если Lead способен качественно закрыть запрос один.

## 6. Внутренняя передача работы (Persona Handoff)

Обязательный typed workflow:

1. Lead формирует `handoff_task` с целью, scope, ожидаемым результатом, доступным контекстом, файлами/artifacts и критериями приёмки.
2. Policy Engine определяет, какие инструменты и данные Co-Agent вправе получить.
3. Co-Agent выполняет свою часть в общем или изолированном workspace в зависимости от риска конфликта.
4. Co-Agent возвращает structured result: изменения, artifacts, assumptions, blockers, validation status и рекомендации.
5. Lead принимает, отклоняет либо возвращает работу на revision.
6. При принятии результат интегрируется в общую задачу.
7. Пользователь получает итог от выбранной Lead Persona, если явно не открыт режим совместной работы.

Handoff должен быть видим в job timeline для сложных задач: например `Зейн: архитектура → Нирвана: UX/UI → Зейн: интеграция → QA`.

## 7. Взаимное ревью и спор

Зейн и Нирвана должны иметь возможность критиковать решения друг друга в рамках специализации.

Примеры:
- Нирвана предлагает тяжёлую анимацию → Зейн оценивает производительность и техническую стоимость.
- Зейн предлагает структуру экранов → Нирвана проверяет usability и может потребовать изменить навигацию.
- Нирвана создаёт презентацию → Зейн проверяет цифры/логические выводы.
- Зейн реализует UI по спецификации → Нирвана делает visual/UX review результата.

Разногласие не должно превращаться в бесконечный цикл. Orchestrator задаёт review budget/iteration limit. Если обе позиции допустимы и выбор субъективен/существенен, Lead либо принимает решение по целям пользователя, либо запрашивает выбор пользователя.

## 8. Субагенты ниже Persona Agents

Зейн и Нирвана могут создавать обычных и динамических субагентов. Эти субагенты находятся ниже Persona Agents и не являются отдельными пользовательскими личностями.

Примеры Зейна:
- Flutter Agent;
- Backend Agent;
- Database Agent;
- Gradle Specialist;
- CMake Specialist;
- Security Agent;
- QA/Build Agent.

Примеры Нирваны:
- UX Agent;
- UI Agent;
- Graphic Agent;
- Motion Agent;
- Media Agent;
- Presentation/Storytelling Agent;
- временный специалист конкретного визуального стиля.

Dynamic Subagent создаётся под конкретную задачу с узким role prompt, ограниченным контекстом, разрешёнными tools и resource budget. После выполнения его рабочий контекст закрывается, а результат возвращается создавшей его Persona Agent.

## 9. Иерархия выполнения

Целевая структура:

`User -> Selected Persona (Lead: Zane or Nirvana) -> Persona Co-Agent when useful -> specialized/dynamic subagents -> Tool Runtime / Workers -> Policy Engine enforcement -> integration/review -> Lead Persona -> User`.

Policy Engine применяется ко всем уровням одинаково. Ни Lead Persona, ни Co-Agent, ни dynamic subagent не могут расширить собственные permissions.

## 10. Общий workspace и защита от конфликтов

Для совместной разработки нужен task workspace с ownership/locking или branch-like staging изменений.

- Параллельные агенты не должны молча перезаписывать один и тот же файл.
- Изменения Co-Agent/subagent должны иметь diff/provenance.
- Integration step обнаруживает конфликты.
- После интеграции запускаются соответствующие validators/tests.
- При конфликте ответственность за финальное техническое объединение обычно у Зейна; за итоговое соответствие UX/visual intent — у Нирваны.

## 11. Контекст и память

Lead Persona получает user conversation + project context + разрешённую память + artifacts.

Co-Agent получает только контекст, необходимый для handoff. Не следует без необходимости дублировать всю историю диалога: это уменьшает стоимость и риск утечки лишнего контекста.

В project memory должны сохраняться принятые межагентные решения, которые важны для последующих чатов проекта: архитектурные решения, design system, технические ограничения и согласованные интерфейсы между компонентами.

## 12. Режимы взаимодействия

Минимально нужны:
- `Single Persona` — второй Persona Agent не нужен;
- `Lead + Co-Agent` — стандарт для комплексных задач;
- `Parallel Work` — независимые части выполняются одновременно, если ресурсы позволяют;
- `Review` — одна persona проверяет результат другой;
- `Handoff Revision` — работа возвращается на исправление;
- `Joint Integration` — объединение технической и creative частей.

Пользователь не обязан вручную выбирать режим: система выбирает его автоматически по задаче. В расширенных настройках позже можно разрешить ручное управление/запрет автоматического Co-Agent.

## 13. Resource Scheduler

Persona collaboration не означает обязательный запуск нескольких тяжёлых локальных процессов. Reasoning может идти через несколько API calls, а тяжёлые tools выполняются через общий Scheduler.

Scheduler обязан:
- ограничивать параллельные builds/renders/browser jobs;
- учитывать CPU/RAM/GPU/VRAM;
- ставить work units в очередь;
- не запускать тяжёлые задачи на телефоне при наличии подходящего desktop worker;
- позволять безопасно параллелить лёгкие reasoning/research задачи.

## 14. Пример полного цикла разработки

1. Пользователь в чате Зейна: `Сделай приложение`.
2. Зейн становится Lead и формирует архитектуру/план.
3. Зейн автоматически делает persona handoff Нирване на UX/UI/design system.
4. Зейн и его coding subagents реализуют техническую часть.
5. Нирвана и её visual subagents готовят/проверяют UX/UI/assets.
6. Integration объединяет изменения.
7. Нирвана выполняет visual/UX review.
8. Зейн выполняет technical review.
9. QA Agent запускает tests/smoke tests/build.
10. Ошибки маршрутизируются тому агенту, чья область затронута.
11. Цикл repair/re-test повторяется до success или объективного blocker.
12. Build Agent создаёт APK/EXE/другой artifact.
13. Выбранный Lead Agent (Зейн) сообщает пользователю результат и отдаёт artifacts.

При аналогичной задаче из чата Нирваны порядок лидерства зеркальный: Нирвана остаётся Lead, а Зейн подключается как Technical Co-Agent.

## 15. Критерии готовности

Функция считается реализованной только если:
- Зейн и Нирвана являются реальными Persona Agents, а не prompt-декорацией;
- выбранная persona остаётся Lead на протяжении задачи;
- Orchestrator автоматически определяет необходимость второй persona;
- работает typed handoff с ограниченным контекстом/tools;
- обе persona могут создавать динамических субагентов;
- работает взаимное review/revision;
- есть conflict-safe integration;
- progress показывает межагентные этапы сложной задачи;
- итоговый ответ и artifacts возвращает Lead Persona;
- Policy Engine и Resource Scheduler применяются ко всей цепочке.
