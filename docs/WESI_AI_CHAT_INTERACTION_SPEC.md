# Wesi AI — Chat Interaction Specification

**Статус:** обязательное нормативное дополнение к `docs/WESI_AI_MASTER_SPEC.md`.  
**Дата фиксации:** 2026-08-15.  
**Область:** обычный текстовый чат Wesi AI, интерфейс диалога и поведение пользовательских turn'ов.

## 1. Умная приоритетная очередь сообщений

Очередь Wesi AI **не является тупым FIFO для всех входящих сообщений**. Если AI уже выполняет задачу, каждое новое сообщение пользователя сначала классифицируется по намерению относительно текущей работы.

Минимальные классы:

1. `CONTROL / INTERRUPT` — немедленная команда остановить, отменить или не продолжать текущую работу;
2. `STEER / CORRECTION` — уточнение или исправление, которое должно изменить уже выполняемую задачу прямо сейчас;
3. `DEFERRED / FOLLOW_UP` — самостоятельная или последующая задача, которую разумно выполнить после завершения текущей работы.

Приоритет обработки:

`CONTROL > STEER > DEFERRED`.

Классификация должна учитывать смысл сообщения и текущий task/job context, а не только фиксированный список ключевых слов.

### 1.1 CONTROL / INTERRUPT — немедленная остановка

Если пользователь пишет, например:

- `стой`;
- `стоп`;
- `прекрати`;
- `отмени`;
- `не делай это`;
- `хватит, дальше не продолжай`;

и по контексту это относится к текущей выполняемой работе, сообщение **не помещается в обычный хвост очереди**.

Wesi AI должна максимально быстро:

- прекратить дальнейшую генерацию/планирование текущего шага;
- отменить ещё не начатые work units текущей задачи;
- попытаться отменить активный cancellable tool/job;
- не запускать следующие tool calls, subagents, builds, renders или writes текущего плана;
- сохранить уже полученный безопасный state/checkpoint, если это применимо;
- показать пользователю, что работа остановлена и что уже успело реально выполниться.

Если уже запущена операция, которую технически нельзя безопасно прервать или откатить, Wesi AI не должна притворяться, что она отменена. Она прекращает все последующие шаги, дожидается фактического статуса неизбежно завершающейся операции и сообщает пользователю реальный результат.

Явная текстовая команда остановки должна работать даже без нажатия отдельной кнопки `Stop/Cancel`. Кнопка остаётся дополнительным быстрым способом отправить тот же control intent.

### 1.2 STEER / CORRECTION — немедленная корректировка текущей задачи

Если новое сообщение исправляет направление уже выполняемой работы, оно не должно ждать, пока AI сначала полностью закончит неправильный вариант.

Примеры:

```text
AI: сейчас меняет экран на светлую тему...
Пользователь: Нет, фон должен остаться тёмным, поменяй только карточки.
-> STEER: учесть немедленно в текущей задаче.
```

```text
AI: начал делать Windows installer...
Пользователь: Ты взял не ту версию, нужна 0.23.1+91.
-> STEER: остановить устаревшие последующие шаги и продолжить уже с правильной версией.
```

```text
AI: анализирует весь репозиторий...
Пользователь: Не весь, проверяй только Android build.
-> STEER: сузить текущий scope, а не завершать старый план целиком.
```

Для `STEER` Wesi AI должна:

- признать correction как изменение активного task context;
- остановить ещё не выполненные шаги, противоречащие новой инструкции;
- не повторять уже корректно выполненную работу без необходимости;
- обновить plan/task state;
- продолжить с ближайшего безопасного этапа уже с новым условием;
- если текущий tool/job можно отменить и его результат после correction бесполезен — отменить его;
- если текущую операцию безопасно отменить нельзя — не запускать зависимые от неё устаревшие шаги и применить correction сразу после получения её фактического результата.

Correction не должна автоматически превращаться в новый независимый пользовательский запрос, если по смыслу она относится к текущей работе.

### 1.3 DEFERRED / FOLLOW_UP — выполнить после текущей работы

Если сообщение не требует менять текущую задачу прямо сейчас, оно помещается в обычную очередь.

Примеры:

```text
Пользователь: Исправь Android build.
Wesi AI: [выполняет задачу A]
Пользователь: И после этого проверь Windows build.
-> DEFERRED #1
```

```text
Пользователь: Сделай аудит проекта.
Wesi AI: [выполняет задачу A]
Пользователь: Когда закончишь, ещё составь список технического долга.
-> DEFERRED #1
```

Для `DEFERRED` действует FIFO внутри обычной очереди:

- текущая задача завершается штатно;
- затем автоматически запускается первый ожидающий follow-up;
- после него следующий;
- ошибка одного deferred turn не уничтожает остальные.

### 1.4 Контекстная переоценка очереди

После `CONTROL` или `STEER` ранее накопленная очередь не должна исполняться вслепую.

Wesi AI должна переоценить ожидающие сообщения относительно нового task state:

- всё ещё актуальные follow-up остаются в очереди;
- пункты, ставшие бессмысленными из-за correction, помечаются как `superseded` и не выполняются;
- дублирующиеся пункты могут быть объединены;
- противоречащие новой явной инструкции пользователя не запускаются;
- если безопасно определить намерение нельзя и цена ошибки существенна, система может запросить короткое уточнение перед необратимым действием.

Пример:

```text
Пользователь: Сделай APK.
Пользователь: Потом ещё собери Windows.
Пользователь: Стой, вообще ничего не собирай — сначала только исправь код.

Результат:
- текущий build останавливается/не продолжается;
- Windows build больше не запускается автоматически;
- активная задача меняется на исправление кода.
```

### 1.5 Сохранение контекста и порядок

Каждый принятый turn обязан сохранять:

- исходный `conversationId`;
- `projectId`;
- связь с активным `jobId/taskId`, если сообщение относится к выполняемой задаче;
- классификацию `control | steer | deferred`;
- текст и attachment metadata;
- timestamp;
- состояние `pending | applied | running | completed | superseded | cancelled | failed`.

Queued turn может содержать текст, вложения либо их комбинацию. Нельзя тихо отбрасывать сообщение только потому, что модель уже отвечает.

Ожидающие сообщения должны быть явно видимы пользователю в интерфейсе. Для deferred queue показываются количество элементов и краткий preview; applied correction/control сообщения должны отображаться в timeline как уже учтённые в текущей работе, а не как «ещё ожидающие».

Очередь должна иметь разумный защитный лимит. При его достижении пользователь получает явное сообщение, а введённый текст/вложения не должны молча исчезать.

### 1.6 Fail-safe семантика

При сомнении между `STEER` и `DEFERRED` система должна учитывать стоимость продолжения неправильной работы:

- если новое сообщение явно исправляет цель, scope, параметры, файл, версию, дизайн, данные или метод текущей задачи — предпочитать `STEER`;
- если сообщение логично независимо от активного шага и может быть выполнено позже без потери смысла — `DEFERRED`;
- явная команда остановки всегда имеет наивысший приоритет.

Нельзя продолжать ресурсоёмкую или необратимую работу только потому, что correction формально оказался вторым сообщением в очереди.

## 2. Интерфейс обычного чата

Интерфейс должен сохранять полный функционал Projects, Universal Attachments, камеры, голосового режима, persona handoff и истории чатов, но использовать современную conversation-first компоновку по ранее утверждённому направлению Claude/Grok/Kimi:

- центральный persona-aware empty state;
- компактный верхний bar;
- drawer/sidebar с проектами и чатами;
- быстрый выбор Зейна, Нирваны и Лобби;
- режимы отображения `Классический` и `Думающий`;
- `Думающий` показывает только безопасное резюме обработки, но не скрытую chain-of-thought;
- видимый таймер текущего ответа;
- inline status/tool events;
- follow-up подсказки после ответа;
- округлый composer с attachments/camera/voice/send controls;
- во время генерации composer остаётся доступным для текстовых уточнений и вложений;
- `CONTROL` и `STEER` должны применяться к активной работе без ожидания ordinary FIFO;
- pending deferred queue отображается рядом с composer и не подменяет уже выполняющийся ответ;
- UI должен различать `остановлено`, `корректировка применена`, `ожидает выполнения`, `superseded` и обычное завершение.

## 3. Совместимость и безопасность

Редизайн и smart queue не должны откатывать уже реализованные возможности Wesi AI. В частности запрещено ради нового UI или preemption удалять или обходить:

- AI Projects и project context;
- embedded camera;
- Universal Attachments и staged/chunked upload;
- local chat persistence/migrations;
- retry/error states;
- Зейн/Нирвана/Лобби;
- persona handoff;
- Policy/permissions ограничения backend;
- подтверждения и Risk Policy для опасных действий;
- фактический статус внешних tool/actions.

`CONTROL`/`STEER` не дают права откатывать уже совершённое внешнее действие фиктивно. Wesi AI всегда сообщает фактический результат и только затем выбирает безопасный следующий шаг.

Названия режимов моделей в UI должны соответствовать реально доступным backend tier'ам. Нельзя показывать активный режим, который не имеет работающего server/Relay маршрута.


## 4. Restart-safe local outbox

До появления отдельного server-owned Job Engine обычный чат использует durable local outbox:

- accepted turn считается принятым только после записи в employee-scoped Hive;
- text-only deferred/steer turn восстанавливается после настоящего restart процесса;
- uncertain inflight turn не переотправляется автоматически, чтобы не продублировать возможные side effects;
- после restart для ещё не переданных серверу файлов сохраняются только metadata, поэтому требуется reattach;
- второй controller того же процесса не должен перехватывать очередь первого;
- CONTROL/STEER сохраняют приоритет над восстановленными deferred turns;
- эта local-outbox семантика не означает перенос тяжёлого L3/L4 выполнения на основной VPS: тяжёлые jobs подчиняются Foreground / Background Execution Policy.
