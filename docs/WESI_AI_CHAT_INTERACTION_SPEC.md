# Wesi AI — Chat Interaction Specification

**Статус:** обязательное нормативное дополнение к `docs/WESI_AI_MASTER_SPEC.md`.  
**Дата фиксации:** 2026-08-15.  
**Область:** обычный текстовый чат Wesi AI, интерфейс диалога и поведение пользовательских turn'ов.

## 1. Непрерываемая очередь сообщений

Если Wesi AI уже обрабатывает запрос, отправка пользователем нового сообщения **не должна отменять, обрывать, заменять или перезапускать текущую генерацию**.

Обязательное поведение:

- текущий ответ завершается штатно и отображается полностью;
- новое уточнение, дополнение или следующий запрос помещается в FIFO-очередь того чата, из которого он был отправлен;
- после завершения текущего запроса первый элемент очереди запускается автоматически, затем остальные элементы обрабатываются строго по порядку;
- ошибка текущего запроса не уничтожает очередь: после фиксации ошибки следующий ожидающий turn всё равно должен быть обработан;
- queued turn может содержать текст, вложения либо их комбинацию;
- queued turn сохраняет привязку к исходному conversation/project и не должен случайно выполняться в другом чате;
- ожидающие сообщения должны быть явно видимы пользователю в интерфейсе, включая количество элементов очереди и краткий preview;
- нельзя тихо отбрасывать сообщение из-за того, что модель уже отвечает;
- очередь должна иметь разумный защитный лимит, а при его достижении пользователь получает явное сообщение, а введённый текст не должен молча исчезать;
- обычная отправка следующего сообщения не является командой остановки текущего ответа.

Прерывание текущей генерации допускается только отдельным явным действием пользователя `Stop/Cancel`, если такая команда доступна в интерфейсе.

Пример:

```text
Пользователь: Сделай аудит проекта.
Wesi AI: [обрабатывает запрос A]
Пользователь: И отдельно проверь Android build.   -> queue #1
Пользователь: И не забудь Windows installer.      -> queue #2

Порядок выполнения:
A полностью завершается
-> queue #1
-> queue #2
```

## 2. Server-owned background execution

После того как сервер подтвердил приём turn/job, **владельцем выполнения становится сервер**, а не Flutter-клиент и не открытый HTTP-запрос приложения.

Обязательное поведение:

- закрытие экрана Wesi AI не отменяет уже принятую сервером задачу;
- сворачивание приложения не отменяет задачу;
- закрытие приложения и выгрузка процесса из памяти не отменяют задачу;
- потеря клиентского HTTP/SSE-соединения после server ACK не должна отменять или откатывать уже принятую задачу;
- сервер хранит durable job/turn record с привязкой к `employeeId`, `conversationId`, `projectId`, persona, tier и позиции в очереди;
- серверная job имеет как минимум состояния `queued`, `running`, `completed`, `failed`, а при поддержке отмены — `cancelled`;
- выполнение очереди сериализуется как минимум на уровне одного conversation: следующий turn того же чата не начинает выполнение раньше завершения предыдущего turn;
- после завершения сервер сохраняет итоговый ответ и verified tool results так, чтобы их можно было получить после перезапуска приложения;
- при повторном открытии того же чата клиент восстанавливает server job statuses и готовые ответы, а не запускает запрос заново;
- follow-up сообщения, отправленные пока предыдущая job выполняется, становятся следующими server-owned jobs **того же чата**;
- `Stop/Cancel` является отдельной явной командой и только она может запрашивать отмену активной job; обычное новое сообщение не является cancel.

Клиентский local durable queue используется только как **outbox до server ACK**. После server ACK источником истины для выполнения, статуса и результата является сервер.

### Граница ACK

- До server ACK: клиент обязан сохранить turn локально и повторить доставку при восстановлении сети/приложения, не теряя текст.
- После server ACK: клиент сохраняет `jobId`/`turnId` и conversation binding; закрытие приложения не влияет на выполнение.
- Повторная доставка одного и того же outbox turn должна быть идемпотентной: client-generated idempotency key не должен создавать две server jobs.

## 3. Интерфейс обычного чата

Интерфейс должен сохранять полный функционал Projects, Universal Attachments, камеры, голосового режима, persona handoff и истории чатов, но использовать современную conversation-first компоновку по ранее утверждённому направлению Claude/Grok/Kimi:

- центральный persona-aware empty state;
- компактный верхний bar;
- drawer/sidebar с проектами и чатами;
- быстрый выбор Зейна, Нирваны и Лобби;
- режимы отображения `Классический` и `Думающий`;
- `Думающий` показывает только безопасное резюме обработки, но не скрытую chain-of-thought;
- видимый таймер текущего ответа;
- inline status/tool events;
- follow-up подсказки после ответа;
- округлый composer с attachments/camera/voice/send controls;
- во время генерации composer остаётся доступным для текстовых уточнений и вложений, которые добавляются в очередь;
- pending queue отображается рядом с composer и не подменяет уже выполняющийся ответ;
- при повторном открытии чата UI показывает актуальные server statuses (`в очереди`, `выполняется`, `готово`, `ошибка`) и затем сохранённый результат.

## 4. Совместимость и безопасность

Редизайн не должен откатывать уже реализованные возможности Wesi AI. В частности запрещено ради нового UI удалять или обходить:

- AI Projects и project context;
- embedded camera;
- Universal Attachments и staged/chunked upload;
- local chat persistence/migrations;
- retry/error states;
- Зейн/Нирвана/Лобби;
- persona handoff;
- Policy/permissions ограничения backend.

Названия режимов моделей в UI должны соответствовать реально доступным backend tier'ам. Нельзя показывать активный режим, который не имеет работающего server/Relay маршрута.

## 5. Надёжность очереди после перезапуска

- UI очищает composer только после того, как outbox turn надёжно записан локально и принят на доставку.
- Text-only turn, который ещё **не получил server ACK**, восстанавливается из local outbox после настоящего перезапуска процесса и повторяет доставку с тем же idempotency key.
- Turn, который **уже получил server ACK**, не переотправляется как новый запрос: клиент восстанавливает его по `jobId`/`turnId` и запрашивает status/result у сервера.
- Серверная `running` job после перезапуска клиента продолжает выполнение в фоне.
- Для local-outbox turn с вложениями сохраняются только безопасные metadata (имя/MIME/размер); bytes/Base64/localPath не сохраняются. Если файл ещё не успел получить server ACK/staged ownership, после рестарта требуется явное повторное прикрепление.
- После успешного staged upload и server ACK дальнейший lifecycle вложения является серверным и не зависит от приложения.
- Второй controller в том же процессе не должен создавать дубликаты delivery/job; idempotency и server job identity являются обязательными.
