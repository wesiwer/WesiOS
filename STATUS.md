## Сессия 2, часть 3 — подтверждённые архитектурные решения

Пользователю заданы 2 вопроса (см. предыдущую часть) — оба решены:

### Fullscreen при старте — подтверждено, реализовано

Пользователь подтвердил: нужен настоящий OS fullscreen, несмотря на то что это
ломает системный minimize (как и предупреждалось). Нашёл точную причину в
исходниках плагина `window_manager` (`windows/window_manager.cpp:344`):

```cpp
void WindowManager::Minimize() {
  if (IsFullScreen()) {  // Like chromium, we don't want to minimize fullscreen windows
    return;
  }
  ...
}
```

Это намеренное поведение плагина (как у Chromium) — `minimize()` на Win32
безусловно ничего не делает, если окно в fullscreen. Обойти нельзя, вызывая
`minimize()` напрямую. Решение — обходной путь на уровне приложения:

| Файл | Изменение |
|---|---|
| `lib/main.dart` | `windowManager.maximize()` → `windowManager.setFullScreen(true)` при старте. |
| `lib/core/widgets/window_controls.dart` | Кнопка «Свернуть» теперь зовёт `_minimize()`: сначала явно `setFullScreen(false)`, потом `minimize()` — на этот момент `IsFullScreen()` уже `false`, и нативный `Minimize()` отрабатывает как обычно. Разведены два разных булевых состояния: `_isFullScreen` (текущее нативное состояние — только для иконки кнопки) и `_wantFullScreen` (выбор пользователя — используется в `onWindowRestore()`, чтобы при восстановлении из трея вернуть fullscreen обратно). Это разделение критично: если бы `onWindowRestore` смотрел на `_isFullScreen`, оно было бы `false` сразу после сворачивания (мы же сами его погасили) — и fullscreen не возвращался бы никогда после первого же minimize. Средняя кнопка (была maximize/restore) теперь переключает fullscreen (`Icons.fullscreen`/`fullscreen_exit`), двойной клик по drag-зоне делает то же самое. |

Проверено по исходнику плагина: `SetFullScreen(false)` — лёгкая операция
(меняет `GWL_STYLE` + `SetWindowPos`, без пересоздания окна), поэтому пара
setFullScreen(false)+minimize() не должна давать заметного визуального
«моргания». **Требует подтверждения на живом билде** — сам Win32 у меня
недоступен для ручной проверки.

## Сессия 2, часть 4 — мульти-движковый прогноз (Wesi Horizon / Prophet / SARIMAX)

Запрос пользователя: тумблер на экране прогноза для выбора движка — родной
(с крутым английским именем, с приставкой Wesi) / Prophet / SARIMAX — плюс
режим сравнения (график и таблица, от 0 до всех 3 сразу) и режим
«Комбинированный» — среднее по тем движкам, что реально посчитались.

### Архитектура

| Файл | Роль |
|---|---|
| `lib/features/treasury/services/multi_engine_forecast.dart` | `ForecastEngineKind` (wesiHorizon/prophet/sarimax/combined), `ExternalForecastBridge` (Dart↔Python подпроцесс), `RiskEstimate` (Cash Gap Risk Score по готовым P10/P50/P90 через нормальную аппроксимацию — нужно для движков без сырых Monte-Carlo путей), `combineForecastResults` (поэлементное среднее, пропускает недоступные движки, не считает их нулём). |
| `python_engines/_io_common.py` | Общий контракт ввода/вывода для обоих внешних движков: JSON `{history: [{date, net}], days, current_balance}` → JSON `{engine, p10, p50, p90, history_days}` или `{error, detail}`. |
| `python_engines/forecast_prophet.py` | Prophet (Meta), `interval_width=0.8` → P10/P90. |
| `python_engines/forecast_sarimax.py` | statsmodels SARIMAX(1,1,1)x(1,1,1,7) с откатом на ARIMA(1,1,1) без сезонной части, если модель не сходится. |

**Родное имя движка: «Wesi Horizon»** — так называется существующий
`ForecastEngine` (bootstrap Monte-Carlo) в UI/сравнении; сам класс не
переименовывался (не имеет смысла менять публичное Dart-имя ради
отображаемой строки — она и так задаётся через `ForecastEngineKind.nameRu/nameEn`).

Ключевое упрощение (задокументировано и в коде, и здесь): Prophet/SARIMAX
прогнозируют **один** ряд — чистый дневной денежный поток (доход минус
расход), в отличие от Wesi Horizon, который считает доход и расход как два
независимых потока (даёт точность и рычаг для «Что если?»). Следствие:
множители «Что если?» к Prophet/SARIMAX не применяются — сценарий влияет
только на Wesi Horizon. Показывать это как недостаток внешних движков было
бы нечестно: это стандартный вход для готовых библиотек временных рядов,
не особенность нашей реализации.

Всё протестировано end-to-end локально (pip install numpy/pandas/statsmodels/
prophet/cmdstanpy, оба скрипта дают корректные P10≤P50≤P90 на синтетических
данных, мост Dart→Python отрабатывает за ~1-1.1 сек на вызов). Юнит-тесты:
`test/multi_engine_forecast_test.dart` (8 тестов — среднее по движкам,
пропуск недоступных вместо нуля, несовпадение длин не роняет приложение,
Cash Gap Risk Score по перцентилям).

### UI (`forecast_chart_screen.dart`)

- `_engineSelector()` — 4 независимых тумблера (Wesi Horizon/Prophet/SARIMAX/
  Combined), с индикатором загрузки на конкретном тумблере (Prophet/SARIMAX
  считаются лениво — только по первому включению, до следующей смены
  периода/сценария) и индикатором «недоступен» (не найден Python/скрипт
  упал — с тултипом-объяснением), а не тихой пустотой.
- График: **ровно один активный движок** → полная деталировка (P10-P90
  заливка/пунктир по существующим тумблерам `_controls()`, но обобщено на
  выбранный движок и его цвет — не только Wesi Horizon, как было раньше).
  **Ноль или 2+** → режим сравнения: только линия P50 на каждый активный
  движок (полосы убраны — иначе нечитаемо), легенда под графиком.
- `_comparisonTable()` — таблица под графиком, колонка на активный движок,
  равномерная выборка дней (не более 12 строк — полный список на 365-дневном
  горизонте не поместится и не нужен).
- Цвета движков: Wesi Horizon — существующий `accentOrange`; Prophet —
  `#38BDF8` (голубой); SARIMAX — `#C084FC` (фиолетовый); Combined —
  `#2DD4BF` (бирюзовый) — те же оттенки, что уже использованы в пресетах
  `wesi_avatar.dart`, ничего нового в палитру не добавлено.

Python подпроцессом — desktop-специфичный паттерн; для Android потребовался
бы принципиально другой подход (например, Chaquopy или облачный API) —
новое архитектурное решение, не часть этого захода.

### Почему zip-скачивание, а не `pip install` на машине пользователя

У обычного пользователя нет C++ тулчейна для сборки CmdStan (Prophet) —
`cmdstanpy.install_cmdstan()` на его машине просто упадёт. Поэтому вся
тяжёлая работа (pip install, компиляция CmdStan) сделана **один раз в CI**
(`build-engines.yml`, тот же приём, которым в прошлой части этой сессии
собирался и тестировался бандл), результат — готовый к использованию
`python/` каталог, упакованный в zip. Пользователю остаётся только
скачать и распаковать — операции, для которых не нужен ни компилятор,
ни интернет-соединение к PyPI на каждый пакет по отдельности (один файл,
предсказуемый прогресс).

Важный технический нюанс с CmdStan: путь до собранного CmdStan **не может
быть абсолютным путём времени сборки** (на CI-раннере это один путь, у
пользователя бандл окажется совсем в другом месте — в `ApplicationSupport`).
`forecast_prophet.py` поэтому ищет `cmdstan/` каталог **относительно
`sys.executable`** (а не по зашитому в файл абсолютному пути) — первая
версия этого решения именно так и была ошибочно написана (маркер-файл с
абсолютным CI-путём), поймано и исправлено при код-ревью до пуша.
Проверено вручную (символическая ссылка на реальный локальный CmdStan
в каталоге рядом с `sys.executable`, скрипт находит и использует его
корректно).

### ⚠️ build-engines.yml пока нельзя запустить — GitHub-ограничение, не баг

`workflow_dispatch` по API регистрирует только те workflow-файлы, которые
уже есть в **дефолтной ветке** репозитория (main/master). `build-engines.yml`
существует пока только в `claude/document-review-wp4jch` — GitHub его
попросту не видит: `list_workflows` показывает только `build.yml`, а
попытка дёрнуть `build-engines.yml` возвращает `404`. Это значит, что
**реальных zip-файлов в GitHub Release `engines-v1` пока нет** — кнопки
«Скачать» в приложении корректно провалятся с ошибкой сети (fail-soft
сработает, `InstallStage.failed`, без падения), но по-настоящему установить
Prophet/SARIMAX через них сейчас нельзя. Три пути:
1. Смёржить эту ветку в main/master — тогда `build-engines.yml`
   зарегистрируется сам, и его можно будет запустить как обычно.
2. Дать явное разрешение запушить `build-engines.yml` напрямую в
   дефолтную ветку отдельно от остального (сам этого делать не стал —
   правило «не пушить в другую ветку без явного разрешения»).
3. Запустить вручную через GitHub UI (вкладка Actions → workflow
   поддерживает выбор ветки в самом интерфейсе иначе, чем API — стоит
   проверить, действует ли то же ограничение и там, я не проверял).

### Что не автоматизировано (сознательно)

- Резюмируемость закачки (докачать с места обрыва при потере соединения) —
  не реализована. Обрыв = закачка начинается заново. Для 350 МБ/1,7 ГБ на

- Проверка целостности скачанного zip (контрольная сумма/подпись) — не

## Сессия 2, часть 9 — автообновление, счета, аналитика

### Автообновление приложения

CI (`.github/workflows/release-app.yml`) публикует Windows-zip и APK как
ассеты Release под **постоянным** тегом `app-latest`, рядом — `app-manifest.json`
с версией и размерами. Ссылка на манифест зашита в код и не меняется никогда:
иначе получалась бы курица и яйцо — чтобы узнать о новой версии, нужно было
бы уже знать её адрес. Манифест публикуется ПОСЛЕДНИМ и только если обе
сборки прошли, иначе приложение предложило бы обновиться на версию, ассета
которой нет.

| Платформа | Как ставится |
|---|---|
| Android | APK отдаётся системному установщику. Нативная часть в `MainActivity.kt`: с Android 7 передавать `file://` наружу запрещено (FileUriExposedException) — нужен FileProvider и `res/xml/file_paths.xml`; с Android 8 установку разрешает отдельное разрешение `REQUEST_INSTALL_PACKAGES` у конкретного приложения, и если его нет, пользователя отправляет ровно в нужный экран настроек, а не в молчаливое ничего. |
| Windows | Сборка портативная, поэтому «установка» — подмена файлов. Своё же приложение переписать на ходу нельзя (exe заблокирован, пока процесс жив), поэтому пишется `.bat`: ждёт завершения процесса, распаковывает архив поверх папки, перезапускает приложение и удаляет сам себя. |

**Сравнение версий покомпонентное, а не строкой.** Как строки «0.10.0» меньше
«0.9.0» — после десятого минора обновление перестало бы предлагаться вовсе.
На это есть тест.

### Счета внутри Wesi Inc

Общий баланс разбивается на любое число счетов (`AccountModel`, typeId 15;
`AccountKind` — 14). Операция принадлежит счёту, общий баланс — сумма по всем.

Совместимость: у операций, созданных до появления счетов, `accountId` равен
`null`, и они трактуются как операции основного счёта
(`TransactionModel.effectiveAccountId`). Если бы такие записи просто выпали
из выборки, баланс обнулился бы сразу после обновления — на это есть тест.

Основной счёт удалить нельзя, счёт с историей архивируется, а не удаляется.
Баланс и разрезы считаются по **выбранному** счёту: иначе переключение
меняло бы список операций, а цифры сверху оставались бы общими.

### Аналитика — полноценная вместо заглушки

`features/analytics/services/analytics_service.dart` — чистый расчёт поверх

## Сессия 2, часть 10 — Wesi Shield

Прежний замок (`vault_lock_service.dart`) закрывал одну секцию с ключами
Firebase одиночным SHA-256 с солью. Он удалён; на его месте

### Что изменилось по сути, а не по названию

| Было | Стало | Зачем |
|---|---|---|
| Один проход SHA-256 | PBKDF2-HMAC-SHA256, 120 000 итераций | Одиночный SHA-256 считается миллиардами хэшей в секунду на обычной видеокарте: короткий пароль подбирался бы за минуты **даже с солью**. Итерации делают перебор дороже на пять-шесть порядков, а у владельца отнимают доли секунды. |
| `==` при сравнении хэшей | Сравнение за постоянное время | Обычное `==` выходит на первом различии, и по времени ответа хэш подбирается посимвольно. |
| Неограниченные попытки | Экспоненциальная пауза: 15 с, 30 с, 1 мин… с потолком 15 мин | Иначе подбор упирается только в стойкость хэша, но не во время. Потолок обязателен — без него забытый пароль превращает устройство в кирпич. Первые две попытки без штрафа: опечатка не должна наказывать владельца. |
| Закрыта одна секция | `ShieldScope`: только ключи **или** всё приложение | Финансы и задачи защищать было нечем. |
| — | Автоблокировка по бездействию (0/1/5/15/30 мин) | Самый частый способ «оставить открытым» — просто уйти. Активность слушается один раз на уровне приложения (`ShieldGate`), а не в каждом экране: продублированное однажды забывается. |
| — | Журнал последних 50 событий | Без него неудачные попытки входа не видны вообще. |
| — | Необязательное стирание данных после N неудач | Выключено по умолчанию и подписано красным: необратимо. |

### Детали, которые видно только в коде

- **Пароль по-прежнему не хранится** — только соль, число итераций и
  производный ключ. Число итераций пишется рядом с хэшем: без него понизить
  стойкость можно было бы, просто подменив счётчик.
- **PBKDF2 написан вручную** (пакет `crypto` даёт только Hmac) и потому
  проверен **тремя официальными тест-векторами RFC 6070**. Без них «работает»
  значило бы только «не падает»: самодельный KDF может давать стабильный, но
  неправильный и потому более слабый результат.
- **Старый пароль продолжает подходить.** При успешном входе он молча
  переводится на PBKDF2, слабый SHA-256 стирается, включённая биометрия
  переносится. Момент выбран не случайно: только при входе пароль известен
  в открытом виде. Неудачная попытка старый хэш **не** трогает — иначе чужая
  ошибка отрезала бы владельца от собственных ключей.
- **Замок стоит в Overlay ниже кнопок окна.** Поставь его выше —
  заблокированное приложение нельзя было бы ни свернуть, ни закрыть, только
  снять из диспетчера задач. На это есть тест, и он падает при обратном
  порядке (проверено переворотом).
- **Стирание чистит и `wesios_cache`/`wesios_offline_queue`.** Стереть
  основное и оставить копию значит не стереть ничего.
- Оценка защищённости — не «насколько вы в безопасности вообще», а насколько
  использованы меры, которые приложение реально умеет. Обещать больше было бы
  враньём.

### Календарь: связь с задачами доведена до конца

В прошлом отчёте «связь календаря и задач» была отмечена сделанной. Это
было верно наполовину: сроки задач появились на **главной** (`HomeAgenda`),
а сам экран «Календарь» до сих пор рисовал заглушку — «события появятся
здесь, когда календарь свяжут с задачами и регулярными платежами».

Теперь календарь читает реальные данные:

- на датах — точки: синяя (задачи), красная (есть просроченная), оранжевая
  (регулярное списание). Точки, а не числа: в ячейке 42 px цифра рядом с
  датой читается как часть даты;
- под сеткой — что именно в этот день: задачи со статусом и платежи с
  суммой, нажатие ведёт на доску или в операции;
- подписка на `revision` задач и Treasury — экран открывается поверх
  вкладок и не пересоздаётся при возврате.

Стадия модуля осталась «частично»: отдельных событий, повторяющихся
напоминаний и режимов недели/года по-прежнему нет. Строку «Отметки на
датах» из списка планов убрал — обещать сделанное нечестно.

### Один расчёт повторений на всех

`core/services/recurrence.dart` — `occursOn` (нужен календарю) и
`nextOccurrence` (нужен уведомлениям). До этого арифметика жила внутри
`AlertService`; вторая копия для календаря разошлась бы с первой при первой
же правке. Есть тест, который прямо проверяет их согласованность: дата, что
вернул `nextOccurrence`, обязана проходить `occursOn`.

Отдельно проверено то, что легко не заметить: **недельный платёж через
перевод часов**. Разница дат считается в UTC, потому что в зоне с переводом
стрелок сутки бывают 23 или 25 часов, и `difference().inDays` на местных
датах даёт шесть дней вместо семи — платёж начал бы пропадать раз в
полгода. Тест прогоняет 26 недель подряд.

### Настройки: семь мёртвых элементов

Поиск по `onTap: () {}` нашёл ещё семь: шесть плиток в настройках и
переключатель «скрыть финансовые данные» с `onChanged: (_) {}`. Два из них
были не просто бесполезны, а **писали неправду**: push- и email-уведомления
значились «включены» — при том, что ни того, ни другого в приложении нет.

Что стало:

| Было | Стало |
|---|---|
| «Push-уведомления — включены» | Пометка «в планах», подпись «нужен сервер», не нажимается |
| «Email-уведомления — включены» | То же |
| «Telegram-бот — подключить» | То же |
| Тема со стрелкой | Тема в приложении одна — пометка «в планах» |
| «Экспорт резервной копии» | **Работает**: JSON + системное «поделиться» |
| «Очистить кэш» | **Работает**: подтверждение с числом записей, затем очистка |
| Переключатель приватности | **Работает**: суммы по всему приложению |

**Резервная копия** (`core/services/backup_service.dart`) — обычный JSON с
отступами, а не дамп Hive: копия, которую нечем прочитать, не копия.
Настройки в неё намеренно не входят — там лежат ключи Firebase и хэш пароля
Shield, и класть их в файл, который человек перешлёт себе в мессенджер, это
ровно та дыра, от которой Shield и защищает. Встроенные статьи тоже не
выгружаются: они приезжают с обновлением и только раздували бы файл.

**Очистка** сначала считает, сколько записей исчезнет, и показывает это
число: спрашивать «точно удалить?» без числа значит спрашивать ни о чём.

**Режим приватности** маскирует суммы в `CurrencyService`, а не в каждом
экране: иначе в следующем новом экране про него забыли бы. Тесты проверяют
не «стало ли красиво», а что не просачивается: ни одной цифры ни в одной
из форм вывода, и **знак минуса тоже скрыт** — по одному «-» было бы видно,
что дела плохи, а прятали именно это. Значок валюты остаётся: скрыта сумма,
а не то, в чём она. `display()` продолжает отдавать настоящее число —
маскируется вывод, не данные.

Перестроение при переключении сделано один раз в `app.dart` поверх всего
дерева: вкладки живут в `IndexedStack` и сами не обновятся.

### Очистка не работала — и сообщала об успехе

Первая версия и очистки, и стирания у Shield делала так:

```dart
if (Hive.isBoxOpen(name)) await Hive.box<dynamic>(name).clear();
```

Hive сверяет тип значений и на боксе, открытом сервисом как
`Box<TransactionModel>`, бросает «already open and of type». Исключение
уходило в `catch (_)`, и снаружи это выглядело как «всё прошло»: настройки
писали «Локальные данные удалены», а данные оставались на месте. У Shield
было хуже — не срабатывало **стирание после N неудачных попыток**, то есть
функция защиты молча не делала того, что обещала.

Проверено не рассуждением, а отдельным прогоном: `Hive.box<dynamic>` на
типизированном боксе бросает, и после «очистки» в боксе остаётся 1 запись.

Починено: `BackupService.openedBox` возвращает бокс с его настоящим типом.
`ShieldService._wipeData` теперь вызывает `BackupService.clearLocalData` —
один список боксов и одно знание об их типах на двоих; своя копия здесь
однажды отстала бы.

Тесты открывают боксы **ровно так же, как их открывают сервисы** — с
конкретными типами. Иначе они бы прошли и на сломанном коде. Проверено
переворотом: с прежним `Hive.box<dynamic>` падают три теста, включая
«действительно стирает, а не сообщает об этом».

### ⚠️ Автообновление не может работать, пока репозиторий приватный

Проверено запросом, а не рассуждением:

```
404  https://github.com/wesiwer/WesiOS/releases/download/app-latest/app-manifest.json
404  https://github.com/wesiwer/WesiOS/releases/download/app-latest/wesios-android.apk
404  https://github.com/wesiwer/WesiOS                        (сам репозиторий)
```

`AppUpdateService.check()` ходит по анонимной ссылке без токена. Репозиторий
приватный, значит GitHub отдаёт **404 всем**, включая приложение. Код
написан правильно и собирается, релизы публикуются — но проверка обновлений
не найдёт их никогда.

Раньше это было **невидимо**: на не-200 сервис молча возвращал `null`, и
снаружи «обновлений нет» и «проверить не смог» выглядели одинаково. Человек
месяцами сидел бы на старой версии, считая её свежей. Теперь при нажатии
«Проверить» видно причину прямым текстом. При фоновой проверке на старте
по-прежнему тихо: красный баннер каждый запуск про то, что из приложения не
починить, — это шум.

Починить можно только снаружи приложения, и это решение владельца:

1. **Сделать репозиторий публичным** — ссылки заработают как есть, ничего
   в коде менять не нужно. Но исходники станут открытыми.
2. **Отдельный публичный репозиторий только под релизы** — исходники
   остаются закрытыми, в `releaseFileUrl` меняется адрес, workflow
   публикует ассеты туда.
3. **Свой хостинг** манифеста и файлов.

Токен в само приложение зашивать нельзя: APK распаковывается, и токен от
приватного репозитория оказался бы у всех, у кого есть сборка.

До этого сборки ставятся вручную со страницы релиза `app-latest`.

### Прогноз песочницы + свои сценарии «Что если?»

`features/treasury/sandbox_forecast_screen.dart` + `services/what_if_store.dart`.

Отличие от прогноза в Treasury: там сценарий один и живёт до закрытия экрана.
Здесь сценарии **именованные и сохраняются**, а на графике одновременно
рисуются базовая линия и все включённые сценарии — видно не «что будет», а
«что будет при каждом из моих вариантов» рядом. Под графиком — словесный
разбор: конечный баланс, разница с базовым, день ухода в минус, день риска
кассового разрыва.

Два решения, которые стоит помнить:

- Событие сценария хранится как **смещение в днях**, а не абсолютная дата.
  Сценарий «крупная закупка через 2 недели» должен оставаться осмысленным и
  через месяц; прибитая дата к тому времени уехала бы в прошлое, а движок
  игнорирует события не позже сегодняшнего дня — сценарий молча перестал бы
  работать. Смещение ≤ 0 подтягивается к 1 по той же причине.
- Хранилище — нетипизированный Hive-бокс с JSON, а не `TypeAdapter`. Сценарий
  это конфигурация, её форма будет меняться; JSON переживает добавление поля
  без миграции адаптера и без нового typeId.

Проверено воспроизведением: `python -P` (тот же режим) даёт ту же ошибку на

### Ловушка при написании виджет-тестов доски (стоила часа)

`testWidgets` крутит тело теста в `FakeAsync` с поддельными часами. Hive
пишет на **реальный** диск, поэтому `await box.put(...)` внутри тела теста не
завершается никогда: тест виснет до таймаута и не печатает ни одной строки
об ошибке — выглядит как зависшая раскладка, хотя раскладка ни при чём.

Правило: любые открытия бокса и записи — только в `setUp`/`setUpAll`, где
асинхронность настоящая. Внутри `testWidgets` допустимо лишь чтение уже
открытого бокса: оно резолвится микротаской, а её FakeAsync прокручивает.
Второе: `pumpAndSettle` на этом экране тоже не вернётся, пока висит
`CircularProgressIndicator` (анимируется бесконечно) — нужен `pump`.

Сами тесты доски проверяют её на 1280×800 и 390×844, при 6 и 30 задачах в
колонке и на пустой доске. Заодно проверено, что исходная раскладка колонки
(`Flexible` + `shrinkWrap`) тоже проходила — переход на
`Expanded` + `ListView.builder` сделан не как исправление дефекта, а чтобы
колонки были одной высоты и карточки не материализовались все разом.

## Сессия 2, часть 6 — версионирование движков и обновления

Вопрос пользователя, вскрывший реальную дыру: «будет ли скачиваемая версия
актуальной через 5 лет?». Была — нет: тег `engines-v1` зашит намертво, внутри
zip лежит то, что pip поставил в день сборки, и ничто никогда бы это не
обновило. Файл с GitHub Release не пропадёт (ассеты хранятся бессрочно), но
через 5 лет внутри был бы statsmodels пятилетней давности на Python 3.11,
у которого к тому моменту кончится поддержка.

### Манифест — как приложение узнаёт о новой сборке

Ключевая идея: **тег Release не равен версии движка.** `engines-v1` — просто
стабильный адрес, по которому всегда лежит актуальная сборка (CI
перезаписывает ассеты через `--clobber`). Фактическая версия живёт в
`manifest.json` рядом с zip-ами:

```json
{"schema": 1, "engines": {
  "sarimax": {"version": "2026.07.28", "asset": "...zip",
              "sizeBytes": 367001600,
              "packages": {"statsmodels": "0.14.6", ...}}}}
```

Приложение тянет манифест (кэш 6 ч, принудительно — при заходе в Настройки),
сравнивает `version` с записанной в Hive при установке, и если отличается —
показывает предложение обновиться **тем же баннером и тем же разделом
настроек**, что и первую установку (как и просил пользователь). Версия
пишется в Hive **только после успешной распаковки** — оборванная установка
не должна выглядеть как «актуальное уже стоит».

Благодаря манифесту приложению **не нужен новый релиз, чтобы узнать о свежем
движке** — иначе обновление движка требовало бы обновления самого WesiOS,
что делало бы всю затею бессмысленной.

Сравнение версий — на **неравенство**, а не «больше/меньше»: версии это даты
сборки, и если сборку на сервере откатили назад (нашли брак), честнее
предложить синхронизироваться с текущей серверной, чем молча оставить
пользователя на отозванной.

### Автоматическая пересборка + smoke-тест

`build-engines.yml` теперь гоняется **по расписанию — 4-го числа каждого
месяца** (не 1-го и не в полночь, когда Actions перегружен), плюс вручную.
Пакеты намеренно **не запинены по версиям**: смысл ежемесячной пересборки
именно в том, чтобы подтянуть свежие statsmodels/prophet с PyPI.

Страховка от сломанного апстрима — **smoke-тест перед публикацией**: свежесобранный
движок прогоняется на детерминированном наборе данных
(`python_engines/_smoke_test_input.json`, 30 дней, без random) и обязан выдать
7 точек прогноза с корректным порядком P10 ≤ P50 ≤ P90. Не выдал — job падает,
публикации не происходит, у пользователей остаётся предыдущая рабочая сборка.
Для Prophet этот тест заодно проверяет самое хрупкое место бандла: что скрипт
реально находит собранный CmdStan относительно `sys.executable`.

Манифест публикует **отдельная третья задача** (`publish-manifest`,
`needs: [build-sarimax, build-prophet]`) — строго после того, как ОБА бандла
собрались и прошли smoke-тест. Иначе манифест мог бы пообещать версию,
которой на сервере нет.

### Тесты

`test/engine_manifest_test.dart` — разбор ровно того JSON, который генерирует
`publish-manifest` (если формат манифеста в workflow разойдётся с парсером,
тест поймает это здесь, а не у пользователя в виде «обновления никогда не
предлагаются»), плюс устойчивость к битым/неполным записям.

### Что здесь по-прежнему остаётся вручную

Цепочка «вышел новый statsmodels → пользователь видит предложение обновиться»
полностью автоматическая только в пределах месяца (до следующего запуска по
расписанию). Мгновенной реакции на релиз апстрима нет и не планировалось —
для финансового прогноза это и не нужно, а следить за PyPI в реальном
времени означало бы отдельную инфраструктуру.

## Сессия 2 — продвинутый прогноз, аудит Treasury/Sandbox/кошелька

Запрос пользователя: разобрать систему прогноза и сделать её максимально
точной; проверить Wesi Treasury и «кошелёк» (Home) на логические и визуальные
баги; всё, что чинится в Treasury, зеркалить в Sandbox (идентичное поведение,
изолированные данные); везде поднять версию приложения.

### Новый движок прогноза — настоящий bootstrap Monte-Carlo

Старый `generateForecast` был **не тем, чем себя называл**: комментарий в коде
гласил «non-linear, Monte-Carlo inspired», но по факту это было одно случайное
блуждание с `Random(42)` и аналитической нормальной шириной полосы
(`p50 ± 1.28×spread`) — не симуляция путей, а формула.

Новые файлы (`lib/features/treasury/services/`):

| Файл | Что делает |
|---|---|
| `forecast_engine.dart` | `ForecastEngine.generate(...)` — общий для Treasury и Sandbox. Разделяет историю на детерминированные регулярные платежи (проецируются по датам) и «шум»; считает сезонность по дню недели, EWMA-тренд (полураспад 10 дней, устойчивее плоского окна), bootstrap-семплирование реальных остатков (сохраняет асимметрию расходов, не нормальное распределение); аномалии исключены из фонового шума, но участвуют как риск редкого «шока» с исторической частотой. Запускает 1000 траекторий и считает P10/P50/P90 **эмпирически** по итогам симуляции, а не по формуле. Возвращает `ForecastResult` с диагностикой (сколько дней истории, сколько путей, учтена ли сезонность). |
| `anomaly_engine.dart` | Детекция аномалий на MAD (median absolute deviation) вместо обычного z-score — старый метод считал stdDev по тем же выбросам, которые искал (эффект маскировки: один гигантский расход раздувал stdDev настолько, что переставал быть аномалией по собственной метрике). Порог modified z-score 3.5 — стандартная рекомендация (Iglewicz & Hoaglin). |
| `recurring_engine.dart` | Общая логика регулярных платежей: проекция будущих начислений по датам (с клампом на короткие месяцы/29 февраля) + исправленная due-проверка (см. баг ниже). |

`TreasuryService`/`SandboxService` теперь **делегируют** в эти движки вместо
собственных копий алгоритма — гарантирует идентичное поведение (запрос
пользователя), при этом данные остаются в разных Hive-боксах (изоляция).
Юнит-тесты: `test/treasury_engines_test.dart` (9 тестов — детерминированность
при отсутствии шума, упорядоченность перцентилей, клампы дат, регресс-тест на
баг due-даты, MAD-детекция).

### Дополнения к прогнозу (тот же запрос — «максимально точный»)

- Регулярные платежи (зарплата, подписки) теперь **явно проецируются** на будущие дни по датам, а не размываются в общем шуме — статистически корректнее.
- 4-й режим графика — «Тепловая карта» (сезонность по дню недели, bar-график Пн–Вс) — прямой побочный продукт нового движка, использует существовавший, но ранее неприменённый локальный ключ `weekly_activity_heatmap`.
- Диагностика прямо на экране: «На основе N дн. истории · M симуляций Монте-Карло · с учётом дня недели / мало истории для сезонности» — прозрачность вместо слепого доверия к цифрам.
- Экран честно показывает «Недостаточно данных для прогноза» при <3 транзакциях вместо прежнего пустого/непонятного состояния.
- Видимое окно истории на графике теперь масштабируется с горизонтом прогноза (`clamp(30, 90)`) — 90-дневный прогноз получает пропорциональный контекст истории, а не всегда фиксированные 30 дней.

### Сверка с ТЗ пользователя: 3-слойная архитектура

Пользователь прислал развёрнутый план идеального прогноза (Hard Logic / Adaptive
statistical-ML / Monte Carlo) и попросил свериться, всё ли реализовано.

| Слой | Требование | Статус | Комментарий |
|---|---|---|---|
| 1. Hard Logic | Детерминированные будущие события (зарплата, аренда, подписки, кредиты) с учётом календаря/переноса выходных | ✅ | `RecurringEngine` — проекция по датам с клампом коротких месяцев и 29 февраля. Перенос на выходные (зарплата 1-го числа, выпавшего на субботу, → пятница) **не реализован** — календарь дат сейчас чисто григорианский, без учёта рабочих/выходных дней. |
| 2. Adaptive statistical/ML | Prophet (Meta) / SARIMAX / Holt-Winters для плавающих категорий, авто-детекция дня недели/сезонности/тренда | ⚠️ частично, другой стек | Реализовано: авто-детекция сезонности по дню недели (7 множителей, тест на достаточность истории) + EWMA-тренд (адаптивный, не фиксированное окно) — статистически тот же класс задачи, что решает Holt-Winters (уровень + тренд + сезонность), но написано нативно на Dart, а не через Prophet/statsmodels. **Prophet/SARIMAX как таковые не подключены** — это Python-библиотеки, их интеграция потребовала бы отдельного backend-сервиса и сломала бы оффлайн-архитектуру (Hive, без сервера). Не стал делать это в одиночку — это ровно то архитектурное решение, которое CLAUDE.md просит согласовывать, а не принимать самостоятельно. Если офлайн-требование не жёсткое — могу вынести это в отдельный процесс (например, локальный Python через `process.run`, или FFI), но это отдельная задача с своими компромиссами (вес дистрибутива, время запуска). |
| 3. Monte Carlo | 5 000–10 000 виртуальных прогонов, P10 (bear) / P50 (median) / P90 (bull) | ⚠️ | Bootstrap Monte-Carlo реализован и статистически корректен (эмпирические перцентили, а не формула), но **1000 путей**, не 5 000–10 000 из ТЗ. Число путей — константа `ForecastEngine.defaultPaths`, увеличить тривиально; не поднимал самостоятельно, т.к. это прямой trade-off производительность/точность на десктопе — 1000 путей уже даёт стабильные перцентили на синтетических тестах, а 10 000 при полном пересчёте на каждое изменение периода/What-If может дать заметную задержку UI. Если нужно — подниму до конкретного числа, скажи, какое соотношение точность/скорость приоритетнее. |

| # | Модуль | Статус | Где |
|---|---|---|---|

решение), и 10 000 путей вместо 1000 (слой 3, тривиально поднять по запросу).

## Сессия 1 — починка сборки + P0/P1/P2

### Сначала — починка сборки

## Архитектура (не баги)

1. `SandboxService` ≠ `TreasuryService` — **намеренное** дублирование на уровне сервиса/хранилища (разные Hive-боксы, разные классы). Статистика (прогноз/аномалии/регулярные платежи) при этом идёт через ОБЩИЕ движки в `lib/features/treasury/services/{forecast,anomaly,recurring}_engine.dart` — так гарантируется идентичное поведение без ручного дублирования кода. Не разводи эти движки обратно по двум сервисам — именно это создавало баги-расхождения (пример: `processRecurringPayments` был только в Treasury).
2. Суммы внутри в RUB-эквиваленте; UI через `CurrencyService.fromRub` / `toRub`.
3. Кастомный title bar (`TitleBarStyle.hidden` + `WindowControls`).
4. Курсы: `ExchangeRateService` → cbr.ru (`scripts/XML_daily.asp`); fallback — exchangerate.host, затем зашитые курсы. Парсер проверен на живом ответе ЦБ от 28.07.2026: разбираются все 54 блока `<Valute>`, все восемь валют приложения присутствуют (USD 78,02 · EUR 88,76 · GBP 103,97 · CNY 11,52 · UAH 1,74 · BYN 27,06 · KZT 0,164).
5. **CI пересоздаёт `windows/`.** Шаг «Wipe broken Windows platform stub» удаляет всю папку и заново генерирует её через `flutter create`, потому что в репозитории лежит неполный огрызок (нет `flutter_window.cpp`, `win32_window.cpp`, `utils.cpp`, `Runner.rc`). Любая правка в `windows/runner/` **в сборку не попадает** — переживает только то, что workflow восстанавливает отдельным шагом (сейчас это иконка). Не чини нативные баги правками в `windows/` — они не доедут.
6. `SetQuitOnClose` должен быть `true`. При `false` `WM_DESTROY` не вызывает `PostQuitMessage`, и после закрытия окна процесс остаётся жить.
7. `lib/core/services/finance_firestore_service.dart` — мёртвый код, исключён из анализа: `cloud_firestore` / `firebase_auth` убраны из pubspec (ломают Windows desktop build), файл ниоткуда не импортируется.
8. Калькулятор — глобальный оверлей в `app.dart` (`CalculatorOverlay`), не route. Закреплённый переживает смену вкладок и не перехватывает клики.
9. `android/app/src/main/res/` отсутствовал в репозитории целиком, хотя `AndroidManifest.xml` всегда ссылался на `@mipmap/ic_launcher`, `@style/LaunchTheme`, `@style/NormalTheme`. Сборка падала на `:app:processReleaseResources` — этого не было видно, потому что раньше билд умирал ещё на компиляции Dart. Ресурсы добавлены; иконки отрисованы из `assets/images/app_icon.png`, launch-тема тёмная под `#09090B`.

## Занятые Hive typeId

Менять нельзя — по ним читаются уже записанные данные.

| typeId | Что |
|---|---|
| 1 | `TransactionModel` |
| 2 | `TransactionType` |
| 3 | `RecurringPeriod` |
| 10 | `TaskStatus` |
| 11 | `TaskPriority` |
| 12 | `SubTask` |
| 13 | `TaskModel` |
| 14 | `AccountKind` |
| 15 | `AccountModel` |
| 16 | `ArticleSection` |
| 17 | `ArticleModel` |

Все четыре адаптера задач регистрируются в `lib/main.dart`. Забыть об этом —
падение в рантайме при открытии бокса, которое `flutter analyze` не ловит.

Боксы без адаптеров (обычный JSON/примитивы): `wesios_cache`,
`wesios_settings`, `wesios_offline_queue`, `wesios_whatif`.

Типизированные боксы: `wesios_treasury`, `wesios_sandbox`, `wesios_tasks`,
`wesios_accounts`, `wesios_knowledge`.
