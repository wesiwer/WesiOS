**Статус:** к реализации

# Часть I. Иерархия организаций в WesiOS

## 1. Цель

Ввести в WesiOS древовидную структуру организаций, где:

- любая организация — полноценная единица с собственными счетами, операциями, людьми, аналитикой и прогнозом;
- `Wesi Inc` — корневая и тоже полноценная организация, а не просто сводка;
- можно строить дерево любой глубины;
- деньги между организациями проводятся явно;
- можно работать:
  - внутри одной организации;
  - по поддереву: организация + все дочерние;
- текущие данные не ломаются;
- рост компании не требует переделки архитектуры.

## 2. Ключевые принципы

1. **Каждый узел дерева = реальная организация.** Не папка, не тег, не фильтр.
2. **Родитель тоже полноценная организация.** У `Wesi Inc` свои счета, расходы, резервы, инвестиции.
3. **Сводка ≠ сама организация.** Сводка по поддереву — режим просмотра, а не замена учёта узла.
4. **Деньги не телепортируются.** Движение между организациями — явные межорганизационные операции.
5. **UI простой, пока дерево маленькое.** Сложность появляется через создание реальных объектов, а не через искусственные “режимы”.
6. **Обратная совместимость.** Текущий пользовательский опыт почти не меняется, пока организация одна / две.

## 3. Термины

| Термин | Значение |
|---|---|
| `Organization` | Узел дерева: `Wesi Inc`, `Wesi Beats`, `IT`, `Studio A` и т.д. |
| `Root` | Корневая организация (`Wesi Inc`) |
| `Parent / Child` | Родитель / дочерняя организация в дереве |
| `Subtree` | Организация + все её потомки |
| `Context` | Текущая выбранная точка работы в дереве |
| `Scope` | `only` = только организация; `subtree` = организация + все потомки |
| `Inter-org transfer` | Явное движение денег между организациями |

## 4. Пользовательские сценарии

### 4.1. Базовый старт

1. В системе есть `Wesi Inc` (`root`).
2. Есть дочерняя `Wesi Beats`.
3. Все данные, уже существующие в WesiOS до внедрения дерева организаций, принадлежат `Wesi Inc`. `Wesi Beats` создаётся дочерней организацией без автоматического переноса туда старой истории.
4. У `Wesi Inc` могут быть свои счета управления / резерва / инвестиций.

### 4.2. Работа внутри организации

Пользователь выбирает `Wesi Beats` и видит:

- только счета Beats;
- только операции Beats;
- прогноз Beats;
- аналитику Beats;
- сотрудников Beats.

### 4.3. Добавление новой ветки

1. В `Wesi Inc` создаётся организация `IT`.
2. Внутри `IT` создаются `Studio A` и `Studio B`.
3. У каждой — свои счета и бюджеты.
4. `Wesi Inc` может инвестировать в `IT` или сразу в студию.
5. Позже можно забирать долю прибыли наверх.

### 4.4. Переключение контекста

Пользователь может выбрать:

- `Studio A`;
- `IT`;
- `Wesi Inc`;

и для каждого выбрать `scope`:

- `only` — только эта организация;
- `subtree` — эта организация + все дочерние.

### 4.5. Межорганизационные деньги

Примеры:

- `Wesi Inc` вкладывает `300 000 ₽` в `IT`;
- `IT` распределяет `100 000 ₽` в `Studio A`;
- `Studio A` через время отправляет прибыль / долю в `Wesi Inc`.

Все движения должны быть видны в истории обеих сторон.

## 5. Модель данных

### 5.1. `Organization`

Обязательные поля:

- `id`;
- `name`;
- `parentId` — nullable; `null` только у root;
- `isRoot` — bool;
- `baseCurrency`;
- `status`: `active | archived`;
- `createdAt`;
- `updatedAt`;
- `createdBy`.

Опциональные поля:

- `code`;
- `description`;
- `color`;
- `sortOrder`.

Ограничения:

- только один root;
- нельзя сделать родителя своим потомком;
- архивирование root запрещено;
- удаление организации с историей запрещено: только `archive`.

### 5.2. Привязка существующих сущностей

Обязательный `organizationId` у:

- `Account`;
- `Transaction`;
- `Category` — либо ownership, либо в будущем shared + override; минимум ownership обязателен;
- `Recurring payment`;
- `Forecast snapshot / prediction records`;
- `Budget / plan`, если есть;
- `Team membership / access grants` в рамках org.

**Базовое правило:**

> Финансовый факт всегда принадлежит ровно одной организации.

### 5.3. `Account`

Дополнить:

- `organizationId`;
- `kind`: `main | reserve | project | cash | card | other`;
- `minimumBalance`;
- `allowNetting`;
- `currency`;
- `archived`.

### 5.4. `Transaction`

Дополнить:

- `organizationId`;
- `accountId`;
- `projectId` — nullable, на будущее;
- `counterpartyId` — nullable;
- `source`: `manual | import | recurring | crm | task | interorg`;
- `createdBy`;
- `updatedBy`;
- `updatedAt`;
- `ownerEmployeeId` — nullable, см. часть II.

Для истории изменений создать отдельную сущность / box `TransactionAudit`:

- `transactionId`;
- `changedBy`;
- `changedAt`;
- `beforeJson`;
- `afterJson`;
- `reason` — optional.

### 5.5. Межорганизационная операция `InterOrgTransfer`

Поля:

- `id`;
- `fromOrganizationId`;
- `toOrganizationId`;
- `fromAccountId`;
- `toAccountId`;
- `amount`;
- `currency`;
- `amountInFromOrgBase`;
- `amountInToOrgBase`;
- `type`: `investment | profitShare | funding | internalTransfer | other`;
- `note`;
- `date`;
- `createdBy`;
- `createdAt`;
- `linkedDebitTransactionId`;
- `linkedCreditTransactionId`.

Правило проведения:

1. Создаётся запись `InterOrgTransfer`.
2. В организации-источнике создаётся расход / списание.
3. В организации-приёмнике создаётся приход / зачисление.
4. Обе транзакции связаны через `transferId`.
5. Удаление — только как согласованная отмена обеих сторон + audit.

## 6. Контекст работы

### 6.1. App Organization Context

Глобальный контекст приложения:

- `currentOrganizationId`;
- `scope: only | subtree`.

Хранение:

- локально на устройстве;
- per-user;
- восстанавливается при запуске.

### 6.2. Правила выборки данных

Если `scope = only`:

- только записи с `organizationId = current`.

Если `scope = subtree`:

- `organizationId in descendants(current) + current`.

### 6.3. Специальные экраны

В контексте одной org:

- обычный Treasury.

В контексте subtree:

- сводные балансы;
- сводные операции;
- сводный риск / прогноз;
- разбивка по организациям.

## 7. Права доступа

### 7.1. Модель доступа

Право выдаётся на:

- конкретную организацию;
- или организацию + всё поддерево.

Минимальные типы прав:

- `view`;
- `view_finance` — агрегированные финансы org/subtree без автоматического доступа к персональным строкам сотрудников;
- `create_transactions`;
- `edit_transactions`;
- `manage_accounts`;
- `manage_recurring`;
- `view_forecast`;
- `manage_org_settings`;
- `manage_members`.

### 7.2. Примеры

- Продюсер `Studio A`: access только к `Studio A`.
- Глава `IT`: access к `IT + subtree`.
- Владелец: full access к `root subtree`.

### 7.3. Ограничения

- нельзя дать доступ к org вне дерева, к которому у пользователя нет пути;
- root-владелец всегда имеет полный доступ;
- финансовые удаления / изменения истории — только роли с соответствующим правом.

## 8. UI / UX

### 8.1. Переключатель организаций

Место: глобальная шапка / Treasury header.

Показывает:

- дерево организаций;
- текущий узел;
- toggle: `Только эта / С дочерними`.

Если организация одна активная и без детей:

- переключатель можно визуально упростить;
- инфраструктура всё равно уже существует.

### 8.2. Экран организаций

Функции:

- дерево;
- создать дочернюю;
- редактировать;
- архивировать;
- открыть настройки org;
- перейти в её Treasury.

### 8.3. Создание организации

Мастер / форма:

1. Название.
2. Родитель.
3. Базовая валюта.
4. Создать стартовые счета — опционально.
5. Назначить участников — опционально.

После создания:

- org появляется в дереве;
- можно сразу переключиться в неё.

### 8.4. Treasury в контексте org

Все основные экраны читают текущий context:

- dashboard;
- operations;
- accounts;
- recurring;
- forecast;
- analytics.

Никаких “глобальных” финансовых списков без org-контекста.

### 8.5. Межорганизационный перевод

Отдельный flow:

1. Откуда: org + account.
2. Куда: org + account.
3. Тип: инвестиция / доля прибыли / финансирование / прочее.
4. Сумма.
5. Дата.
6. Комментарий.
7. Подтверждение.

Результат:

- видно в обеих организациях;
- видно в audit / history.

## 9. Прогноз и аналитика

### 9.1. Локальный прогноз

Считается только по данным выбранной организации при `scope=only`.

### 9.2. Прогноз поддерева

Считается по объединённым данным `org + descendants`.

### 9.3. Учёт межорг потоков

- инвестиции / выводы должны участвовать как known cash events;
- нельзя считать один и тот же поток дважды при консолидации.

### 9.4. Аналитика

Все KPI фильтруются текущим `context/scope`.

В `subtree`-режиме обязательна разбивка “по организациям”.

## 10. Миграция текущих данных

### 10.1. Первый запуск после обновления

1. Создать `Wesi Inc` (`root`), если нет.
2. Создать `Wesi Beats` (`child of Inc`), если нет.
3. Все существующие счета / операции без `organizationId` привязать к `Wesi Inc`.
4. Проставить `organizationId` во все связанные сущности.
5. Сохранить текущий UX: пользователь почти не замечает изменений.

### 10.2. Правила безопасности миграции

- миграция идемпотентна;
- не удаляет историю;
- пишет лог миграции;
- если org уже размечены — повторно не трогает.

## 11. Этапы реализации

### Этап 1 — Фундамент

- сущность `Organization` + tree helpers;
- `organizationId` везде в финансах;
- app context: current org + scope;
- миграция текущих данных;
- базовый org switcher.

### Этап 2 — Treasury в контексте

- accounts / transactions / recurring / forecast фильтруются по context;
- создание счетов / операций всегда в текущей org;
- экран управления организациями.

### Этап 3 — Межорг деньги

- `InterOrgTransfer`;
- проводки в обе стороны;
- история и связи.

### Этап 4 — Права

- access grants на org / subtree;
- enforcement во всех treasury-запросах.

### Этап 5 — Сводка и усиление

- subtree analytics;
- subtree forecast;
- разбивка по узлам;
- удобные действия “инвестировать / забрать долю”.

## 12. Нефункциональные требования

1. **Производительность.** Выборки по org / subtree должны быть быстрыми даже на тысячах операций.
2. **Целостность.** Невозможны новые операции без `organizationId`; невозможны “висящие” счета без org.
3. **Аудит.** Критичные изменения пишутся всегда.
4. **Обратная совместимость.** Старые экраны не деградируют при одной org.
5. **Расширяемость.** Дальше можно добавить projects / cost centers без ломки org-дерева.

## 13. Что НЕ входит в эту версию

- полноценный бухгалтерский план счетов уровня 1С;
- юридический consolidation accounting по всем стандартам;
- сложные approval workflows;
- банковские API open banking;
- автоматический расчёт “% прибыли” по сложным правилам — пока только ручной / полуручной inter-org transfer.

Эти слои можно добавить позже поверх данной модели.

## 14. Критерии приёмки

### Must-have

- есть дерево организаций с root `Wesi Inc`;
- можно создать дочернюю организацию любой глубины;
- у каждой org свои счета и операции;
- переключение контекста меняет все данные Treasury;
- `scope only / subtree` работает;
- межорг перевод создаёт связанные операции в обеих org;
- старые данные мигрированы в `Wesi Inc`;
- нельзя удалить org с историей;
- нельзя создать циклическое дерево.

### Should-have

- права на org и subtree;
- сводная аналитика по subtree;
- история изменений операций.

### Nice-to-have

- быстрые пресеты: “Инвестиция”, “Забор прибыли”;
- визуальная карта дерева с балансами.

## 15. Рекомендуемый порядок внедрения в код

1. `OrganizationModel + storage + tree helpers`.
2. Миграция: `Inc + Beats + backfill organizationId`.
3. `OrganizationContext (current + scope)`.
4. Прокинуть context в `Account / Treasury / Forecast services`.
5. UI switcher + org management screen.
6. `InterOrgTransfer`.
7. `Permissions`.

## 16. Итоговое определение готовности

Фича считается реализованной, если:

> Можно построить дерево `Wesi Inc → IT → Studio A`, вести у каждой свои деньги, переключаться между ними, делать инвестиции / выводы между узлами, смотреть либо один узел, либо поддерево — и при этом вся существовавшая до миграции история остаётся в `Wesi Inc`, а `Wesi Beats` доступна как отдельная дочерняя организация.

# Часть II. Дополнение: персональные показатели сотрудников + руководящий доступ

## 1. Цель дополнения

У каждого сотрудника есть свой финансовый контур показателей.

Примеры:

- программист `Studio A` видит:
  - свои доходы / вклад;
  - свои расходы;
  - свою аналитику;
  - свои задачи / сделки, связанные с деньгами;
- руководитель `Studio A` видит:
  - свои личные показатели;
  - показатели всей `Studio A`;
- глава `IT` видит:
  - свои личные;
  - `IT + дочерние студии` по праву на subtree.

Итоговый принцип доступа:

**личность → роль → организация / поддерево**.

## 2. Базовая модель

### 2.1. Сотрудник

Сотрудник уже существует в командном модуле. Для финансов фиксируем:

- `employeeId / userId`;
- роль;
- привязки к организациям;
- уровень доступа:
  - `self`;
  - `organization`;
  - `subtree`.

### 2.2. Привязка денег к человеку

Операции и денежные события могут иметь ответственного:

- `ownerEmployeeId` — чей это вклад / расход;
- опционально `createdByEmployeeId`;
- для CRM / сделок — `responsibleEmployeeId`;
- для задач с деньгами — исполнитель / ответственный.

**Правило атрибуции:**

> Если деньги можно отнести к человеку — относим.  
> Если нельзя — они остаются только на уровне организации.

## 3. Что такое “личные показатели” сотрудника

Минимальный набор.

### Доходы / вклад

- сделки, которые он закрыл;
- приходы, где он ответственный;
- доля участия — если позже понадобится.

### Расходы

- расходы, где он owner;
- компенсации / выплаты ему;
- связанные с ним регулярные обязательства.

### Эффективность

- `net = его вклад − его расходы`;
- динамика по периодам;
- выполнение плана, если план задан.

### Риски

- просроченные денежные задачи;
- сорванные ожидания по его сделкам;
- аномальные расходы по нему.

Это **не зарплатный расчёт 1С**. Это рабочая финансовая аналитика по человеку внутри WesiOS.

## 4. Уровни видимости

### Уровень 1 — Сотрудник без руководства

Видит только:

- свои показатели;
- свои операции;
- свои сделки / задачи;
- свой личный прогноз вклада, если считаем.

Не видит:

- чужие личные данные;
- весь бюджет студии;
- чужие зарплаты / расходы.

### Уровень 2 — Руководитель узла

Видит:

- свои личные показатели;
- показатели своей организации (`only`);
- при наличии соответствующего права — разбивку по сотрудникам внутри org.

Пример: руководитель `Studio A` видит свой net, net `Studio A`, список людей `Studio A` и их вклад.

### Уровень 3 — Руководитель ветки

Видит:

- свои личные;
- свою org;
- subtree: org + children.

Пример: глава `IT` видит свои показатели, `IT`, `Studio A`, `Studio B`.

### Уровень 4 — Владелец / root

Видит всё дерево и всех людей в рамках root-прав.

## 5. Стыковка с деревом организаций

Доступ сотрудника = пересечение двух вещей:

1. К каким `org / subtree` у него есть право.
2. Какой у него режим просмотра:
   - `self`;
   - `org`;
   - `subtree`.

Примеры:

| Человек | Доступ |
|---|---|
| Программист `Studio A` | `self` в `Studio A` |
| Тимлид `Studio A` | `self + org(Studio A)` |
| Глава `IT` | `self + subtree(IT)` |
| Владелец `Wesi Inc` | `self + subtree(Wesi Inc)` |

## 6. UI-сценарии

### 6.1. Личный кабинет сотрудника / `My Finance`

Экран:

- мой вклад за период;
- мои расходы;
- мой net;
- мои ближайшие денежные события;
- мои просрочки;
- динамика.

### 6.2. Переключение у руководителя

У руководителя в финансах есть переключатель:

- `Мои`;
- `Моя студия / организация`;
- `Ветка` — если есть право на subtree.

**Обязательное правило:** режим `Мои` не заменяется руководящим доступом и не исчезает при повышении роли. CEO / root owner, руководитель ветки и обычный сотрудник всегда сохраняют личный финансовый контур (`self`) в пределах доступных им организаций. Руководящий доступ лишь добавляет `Организация` / `Ветка` поверх `Мои`.

### 6.3. Разбивка по людям

Внутри org-руководителя:

- таблица сотрудников;
- вклад / расходы / net;
- клик внутрь карточки сотрудника.

## 7. Изменения в данных

### 7.1. `Transaction / money event`

Добавить:

- `ownerEmployeeId` — nullable.

### 7.2. `CRM deal / task cash event`

Использовать существующую ответственность и прокинуть её в Horizon / Treasury как owner.

### 7.3. `AccessGrant`

Расширить:

- `employeeId`;
- `organizationId`;
- `includeSubtree` — bool;
- `canViewTeamFinance` — bool;
- `canViewSelfFinance` — bool, обычно true;
- `permissions` — список разрешений.

### 7.4. `EmployeeFinanceSnapshot`

На первом этапе хранить отдельно не обязательно. Считать сервисом на лету:

- self metrics;
- org metrics;
- subtree metrics.

## 8. Правила расчёта

### Личные показатели

Берутся только события, где:

- `ownerEmployeeId = currentEmployee`;
- и org доступна по правам.

### Орг-показатели

Все события org или subtree, без фильтра по owner.

### Важно: зарплата сотрудника

- как расход организации — видна руководителю org;
- в личных показателях сотрудника может отображаться отдельно как “выплаты мне”;
- чужие зарплаты обычным сотрудникам не показываются.

## 9. Прогноз для сотрудника

### Self-forecast

Не полноценный treasury forecast всей студии, а:

- ожидаемые приходы по его сделкам;
- его денежные обязательства;
- его вероятность кассового вклада.

### Manager forecast

Руководитель видит обычный org / subtree forecast + вклад команды.

## 10. Приватность и безопасность

Жёсткие правила:

1. Сотрудник не видит чужие личные финансы по умолчанию.
2. Руководитель видит командный контур только в пределах своего access scope.
3. Root / owner может видеть всё.
4. Любое повышение доступа — только явной выдачей права.
5. Audit “кто смотрел / выгружал чувствительные командные данные” — желательно этап 2+.

## 11. Этапы внедрения — добавка к основному плану

### Этап A — Атрибуция

- `ownerEmployeeId` в операциях и денежных событиях;
- ручное указание ответственного.

### Этап B — Self Finance

- экран “Мои показатели”;
- self analytics.

### Этап C — Manager views

- toggle: `Мои / Организация / Ветка`;
- team breakdown.

### Этап D — Ужесточение прав

- grants на team finance;
- скрытие чувствительных полей.

## 12. Критерии приёмки — дополнение

- у сотрудника есть экран личных финансовых показателей;
- CEO / root owner также имеет отдельный режим `Мои`, несмотря на полный управленческий доступ;
- сотрудник с правом `view_finance` может переключаться между `Мои` и доступной ему организацией; `Ветка` появляется только при subtree-праве;
- обычный сотрудник видит только свои данные;
- руководитель `Studio A` видит свои + `Studio A`;
- глава `IT` видит свои + `IT subtree`;
- можно открыть разбивку по сотрудникам внутри org;
- операции умеют хранить `ownerEmployeeId`;
- нет утечки чужих личных показателей без права.

## 13. Общая архитектура доступа

Итоговая модель:

```text
Дерево организаций
└── права на org / subtree
    └── внутри этого:
        ├── self finance
        └── team/org finance
```

Не отдельно “сотрудник” и отдельно “организация”, а единая система:

> **кто ты → где ты имеешь право → что именно смотришь: себя или контур управления.**

# Часть III. Объединённая архитектурная модель

## 1. Главный invariant ownership

Каждый денежный факт обязан иметь ровно одного владельца-организацию:

```text
moneyEvent.organizationId != null
```

Персональная атрибуция является дополнительным измерением, а не заменой организации:

```text
moneyEvent.organizationId = обязательный org ownership
moneyEvent.ownerEmployeeId = optional person attribution
```

## 2. Контекст выборки

Финансовая выборка строится в следующем порядке:

1. определить доступные организации по `AccessGrant`;
2. применить `OrganizationContext.currentOrganizationId`;
3. развернуть `scope` (`only` или `subtree`);
4. пересечь результат с разрешёнными org;
5. применить view mode (`self`, `org`, `subtree` / manager view);
6. для `self` дополнительно фильтровать по `ownerEmployeeId`;
7. скрыть чувствительные поля, если нет team-finance права.

## 3. Консолидация subtree

При сводке по поддереву:

- внешние денежные события суммируются;
- межорг переводы внутри выбранного subtree не должны удваивать общий cash-flow;
- сами `InterOrgTransfer` остаются видимыми в детализации / history;
- локальные org-балансы сохраняют обе стороны перевода;
- consolidated forecast должен применять elimination внутренних потоков.

## 4. Совместимость с Wesi Horizon

Wesi Horizon обязан получать уже отфильтрованный набор событий по `OrganizationContext` и access scope.

Режимы:

- `only` — локальный forecast узла;
- `subtree` — консолидированный forecast узла + descendants с устранением внутреннего double-counting;
- `self` — отдельный employee contribution forecast, не подменяющий Treasury forecast.

`HorizonPredictionRegistry` / snapshots должны хранить как минимум `organizationId`, а для self-прогнозов при необходимости — `ownerEmployeeId` / view context.

## 5. Сохранение текущего рабочего контура

Миграционный baseline:

```text
Wesi Inc (root)
└── Wesi Beats
```

Все прежние данные без org ownership переходят в `Wesi Inc`. `Wesi Inc` является реальным полноценным root и сохраняет существующие счета, операции, CRM, задачи, категории и Horizon-history. `Wesi Beats` создаётся дочерним контуром и не получает старые данные автоматически.

## 6. Проверка полного результата

Минимальная end-to-end проверка должна доказать одновременно:

1. дерево любой глубины;
2. отсутствие циклов;
3. root нельзя архивировать / удалить;
4. старые данные не потеряны;
5. счета / операции / recurring имеют org ownership;
6. org switcher меняет весь Treasury;
7. `only / subtree` корректно меняют выборки;
8. inter-org transfer атомарно создаёт две связанные проводки;
9. subtree consolidation не считает внутренний перевод дважды;
10. Horizon считает правильный org / subtree context;
11. employee self finance фильтруется по `ownerEmployeeId`;
12. manager access не выходит за выданный org/subtree;
13. обычный сотрудник не видит чужие личные показатели;
14. существующие данные `Wesi Inc` продолжают работать без потери истории, а `Wesi Beats` существует как отдельный дочерний контур.
