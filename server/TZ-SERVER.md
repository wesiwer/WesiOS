# ТЗ: поднять сервер WesiOS

Задача для агента, у которого есть доступ к серверу по SSH.

Автор ТЗ (Claude) доступа к серверу не имеет: работает в изолированном
контейнере, откуда нет маршрута ни к 22, ни к 8090 порту. Всё, что можно было
сделать без сервера, уже сделано — скрипты написаны и лежат в `server/`.
Осталось их выполнить и проверить, что получилось.

---

## Что должно получиться

Одно предложение: **приложение WesiOS на компьютере и на телефоне владельца
показывает одни и те же данные.**

Развёрнуто: на сервере работает PocketBase; в нём есть коллекция
`wesios_records` с правилами доступа и учётная запись; приложение к ней
подключается, и после «Синхронизировать сейчас» операция, заведённая на
компьютере, появляется на телефоне.

---

## Исходные данные

| Что | Значение |
|---|---|
| Сервер | **российский** (Санкт-Петербург), у владельца их два — второй не трогать |
| Доступ | IP, пароль root — взять у владельца |
| Система | Ubuntu 24.04 |
| Ресурсы | 1 ядро, 2 ГБ, 30 ГБ NVMe |
| Порты 25/465/587 | закрыты хостером, почты не будет |

Второй сервер (Нидерланды) в этой задаче **не участвует**. Он под сайт и
Wesi AI, это отдельная работа.

## Шаги

### 1. Установка

```bash
ssh root@АДРЕС
curl -s ifconfig.me; echo    # убедиться, что это нужный сервер
curl -fsSL https://raw.githubusercontent.com/wesiwer/WesiOS/main/server/quick-install.sh -o /root/wesios.sh
bash /root/wesios.sh
```

Скрипт ставит PocketBase службой, настраивает `ufw`, создаёт коллекцию с
правилами и индексом, заводит учётную запись, ставит агента нагрузки и
печатает пароли (он придумывает их сам).

### 2. Если скрипт упал

**Это ожидаемо и это главная часть задачи.** Неизвестность одна: версия
PocketBase. В 0.23 переименовали часть API, и я предусмотрел оба варианта
вслепую, не имея возможности проверить:

| Что различается | До 0.23 | С 0.23 |
|---|---|---|
| Создание администратора | `pocketbase admin create` | `pocketbase superuser create` |
| Вход администратора | `POST /api/admins/auth-with-password` | `POST /api/collections/_superusers/auth-with-password` |
| Поле схемы при создании коллекции | `"schema": [...]` | `"fields": [...]` |
| Описание поля | `{"name","type","options":{...}}` | `{"name","type", ...}` плоско |

`setup-collections.sh` пробует оба варианта и при неудаче печатает ответ
сервера целиком. **Почините под фактическую версию и пришлите правку** —
пусть скрипт работает и дальше, а не только на этой машине.

Если удобнее, версию можно зафиксировать:
`PB_VERSION=0.22.21 bash /root/install-sync.sh`. Но лучше починить под свежую.

### 3. Проверка — обязательная часть

Не «скрипт отработал», а **проверенный результат**. Выполнить и сохранить
вывод:

```bash
# 1. служба жива и переживает перезагрузку
systemctl is-enabled pocketbase && systemctl is-active pocketbase

# 2. сервер отвечает снаружи, а не только с себя
curl -s http://АДРЕС:8090/api/health

# 3. коллекция существует и у неё есть правила
curl -s -X POST http://АДРЕС:8090/api/collections/users/auth-with-password \
  -H 'Content-Type: application/json' \
  -d '{"identity":"ПОЧТА","password":"ПАРОЛЬ"}' | head -c 400
```

Третья команда должна вернуть JSON с полем `token`. Если вернула ошибку —
учётная запись не создалась, и синхронизация не заработает.

```bash
# 4. запись действительно можно положить и прочитать
TOKEN=$(curl -s -X POST http://127.0.0.1:8090/api/collections/users/auth-with-password \
  -H 'Content-Type: application/json' \
  -d '{"identity":"ПОЧТА","password":"ПАРОЛЬ"}' | grep -o '"token":"[^"]*' | cut -d'"' -f4)
UID_=$(curl -s -X POST http://127.0.0.1:8090/api/collections/users/auth-with-password \
  -H 'Content-Type: application/json' \
  -d '{"identity":"ПОЧТА","password":"ПАРОЛЬ"}' | grep -o '"id":"[^"]*' | head -1 | cut -d'"' -f4)

curl -s -X POST http://127.0.0.1:8090/api/collections/wesios_records/records \
  -H "Authorization: $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"owner\":\"$UID_\",\"coll\":\"tasks\",\"rid\":\"probe-1\",\"payload\":{\"x\":1},\"stamp\":\"2026-08-04T12:00:00.000Z\",\"deleted\":false}"

curl -s "http://127.0.0.1:8090/api/collections/wesios_records/records?filter=(coll='tasks')" \
  -H "Authorization: $TOKEN"
```

Вторая команда должна вернуть только что записанное. Это и есть настоящая
проверка: правила доступа, индекс и типы полей проверяются разом.

```bash
# 5. уникальный индекс работает — повтор той же записи должен ОТКАЗАТЬ
# (повторить команду записи из пункта 4; ожидается ошибка, а не второй экземпляр)

# 6. агент пишет показатели
curl -s http://АДРЕС:8090/wesios-status.json
```

После проверки удалить пробную запись:

```bash
curl -s -X DELETE "http://127.0.0.1:8090/api/collections/wesios_records/records/ID_ЗАПИСИ" \
  -H "Authorization: $TOKEN"
```

### 4. Живая проверка из приложения

Попросить владельца:

1. Настройки → Данные → Синхронизация → адрес `АДРЕС:8090`, логин, пароль;
2. «Войти» → должно написать «Вход выполнен»;
3. «Синхронизировать сейчас» → должно написать «Отправлено N, получено M».

Если написало что-то другое — **это и есть находка**, прислать текст дословно.

---

## Что прислать

1. **Версию PocketBase** — `/opt/pocketbase/pocketbase --version`.
2. **Вывод всех шести проверок** из пункта 3.
3. **Правки скриптов**, если что-то чинили — коммитом, не текстом в чат.
4. **Что пошло не так**, если пошло. Дословно, а не пересказом.

Пароли **не присылать в чат** — они уже лежат в
`/root/wesios-credentials.txt` на сервере, владельцу этого достаточно.
Пароль root в чате однажды уже засветили, и его пришлось менять.

## Границы

**Не трогать:**

- ветку `claude/document-review-wp4jch` — на ней идёт работа над приложением;
- код приложения в `lib/` — если нужна правка там, напишите, что именно
  ломается, и её сделает тот, кто эту часть писал;
- `assets/images/wesi_logo_easter.png` — личный логотип владельца;
- второй сервер (Нидерланды).

**Работать в своей ветке**, например `chatgpt/server-setup`. Слияние в `main`
— после проверки.

**Не запускать сборки в GitHub Actions.** Месячная квота минут уже
израсходована однажды 624 автоматическими сборками. Сборка теперь только по
явной команде владельца.

## Что будет дальше (чтобы работа состыковалась)

После сервера следующий шаг — **Wesi AI**. В приложении уже есть контракт, к
которому он должен подойти, — `lib/features/chats/services/ai_topic_judge.dart`:

- обычный `POST {base}/chat/completions` в формате OpenAI;
- заголовок `Authorization: Bearer {ключ}`;
- поля запроса: `model`, `temperature`, `messages` с ролями `system`/`user`;
- ответ разбирается как `choices[0].message.content`.

Адрес, модель и ключ настраиваются в приложении (`AiEndpoint`), так что
подойдёт что угодно, говорящее на этом протоколе: llama.cpp, vLLM, Ollama с
совместимым слоем, свой прокси. **Менять протокол не нужно** — приложение уже
умеет с ним работать, и любые изменения здесь придётся согласовывать.

Первая задача Wesi AI, которая уже ждёт: разметка переписки на темы.
Приложение шлёт окно из нескольких сообщений и ждёт строго JSON
(`split`, `title`, `confidence`, `reason`). Промпты — в том же файле.

Модель для Wesi AI лучше ставить на **нидерландский** сервер: у российского
одно ядро и два гигабайта, и он занят синхронизацией и перепиской.
