# Передача состояния сервера Claude — 2026-08-05

Этот документ фиксирует фактически выполненную настройку российского сервера WesiOS, чтобы Claude и ChatGPT продолжали работу от одного состояния и не повторяли уже сделанное.

## 1. Разделение инфраструктуры

Для WesiOS используется российский сервер Aéza `WesiOS-Data1`.

- ОС: Ubuntu 24.04
- PocketBase: 0.39.10
- Публичный API: `https://api.wesi-inc.ru`
- Панель PocketBase: `https://api.wesi-inc.ru/_/`
- Прямой порт PocketBase: `8090` — временно ещё открыт, позднее нужно закрыть снаружи после полной проверки Nginx

Второй зарубежный сервер не трогать: он предназначен для сайта/модели и не должен использоваться для персональных данных сотрудников.

Секреты, пароли, SSH-ключи и API-ключи в репозиторий не записаны и записываться не должны.

## 3. Архитектура PocketBase

Не создавать отдельные серверные коллекции `tasks`, `contacts`, `operations`, `chats` и т. п.

Текущая архитектура проекта намеренно использует две коллекции:

- `users` — учётные записи;
- `wesios_records` — универсальный журнал синхронизации.

Ожидаемые поля `wesios_records`:

| Поле | Тип | Назначение |
|---|---|---|
| `owner` | text | ID владельца данных |
| `org` | text | будущий общий доступ организации |
| `coll` | text | логический тип сущности |
| `rid` | text | ID записи внутри WesiOS |
| `payload` | json | сериализованная запись |
| `stamp` | text | ISO-время изменения |
| `deleted` | bool | tombstone удаления |

Обязательный уникальный индекс:

```sql
CREATE UNIQUE INDEX idx_wesios_records_unique
ON wesios_records (owner, coll, rid)
```

Текущие правила list/view/create/update/delete должны ограничивать доступ владельцем:

```text
owner = @request.auth.id
```

Поле `org` не удалять. Оно предусмотрено заранее для будущего общего доступа сотрудников.

## 5. Следующая обязательная проверка

Перед изменением Flutter-кода выполнить полный серверный контракт:

1. Получить схему `wesios_records` через PocketBase API.
2. Подтвердить наличие всех семи полей.
3. Подтвердить уникальный индекс `(owner, coll, rid)`.
4. Подтвердить все пять API Rules.
5. Войти отдельным пользователем приложения.
6. Создать тестовую запись.
7. Прочитать её обратно.
8. Обновить её.
9. Проверить отказ при создании дубля `(owner, coll, rid)`.
10. Пометить запись удалённой и проверить обратное чтение.
11. Удалить тестовые данные.
12. После успешного теста заменить старые адреса сервера в приложении на `https://api.wesi-inc.ru`.
13. После проверки приложения закрыть внешний доступ к `8090`, оставив PocketBase доступным только через `127.0.0.1` и Nginx.

## 6. Новая функция: встроенная SSH-консоль

По решению владельца в модуль «Системный администратор» нужно добавить встроенную SSH-консоль по типу мобильного SSH-клиента.

Требования:

- интерактивная SSH shell-сессия с PTY;
- терминальный экран с ANSI-цветами, курсором и историей;
- клавиши Ctrl, Esc, Tab, стрелки и вставка;
- изменение размера PTY;
- повторное подключение и тайм-аут бездействия;
- отдельное разрешение сотрудника `sysadminConsole`;
- перед открытием — Shield/PIN/биометрия;
- основной способ входа — SSH-ключ, не root-пароль;
- закрытый ключ хранить только в системном защищённом хранилище устройства;
- приватный ключ никогда не синхронизировать через PocketBase;
- проверять fingerprint сервера и критически предупреждать об изменении;
- не сохранять содержимое терминала в обычные логи приложения;
- журналировать только факт подключения: пользователь, сервер, время начала и окончания;
- создать на сервере отдельного Linux-пользователя с минимальными sudo-разрешениями вместо постоянной работы под root.

Предпочтительная реализация Flutter: SSH-клиент с PTY и отдельный xterm-совместимый терминальный виджет. Конкретные зависимости перед добавлением проверить по актуальным версиям и совместимости со всеми целевыми платформами.

Приоритет: сначала завершить и доказать синхронизацию PocketBase, затем реализовывать SSH-консоль отдельным этапом.

## 7. Правила совместной работы

- Claude работает в своей ветке.
- ChatGPT работает в своей ветке.
- Не переписывать чужую ветку и не делать прямые конфликтующие изменения.
- Перед переносом в `main` агенты проверяют изменения друг друга.
- Не запускать дорогостоящие сборки GitHub Actions без явной необходимости.
- Все изменения сервера должны быть воспроизводимы скриптом или миграцией и документированы в репозитории.
