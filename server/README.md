# Сервер синхронизации WesiOS

Синхронизация устройств: то, что вы завели на компьютере, появляется на
телефоне, и наоборот. Данные лежат на **вашем** сервере — не у Google и не у
меня.

Сервер: **185.221.199.19** (Санкт-Петербург, 1 ядро / 2 ГБ / 30 ГБ NVMe,
Ubuntu 24.04).

---

## Почему PocketBase

На одном ядре и двух гигабайтах выбор невелик. PocketBase — один
исполняемый файл на Go со SQLite внутри: ему хватает 50–80 МБ памяти,
у него есть учётные записи, права на уровне записей, панель управления и
встроенный Let's Encrypt.

Альтернативы отпадают по памяти: своя Supabase — это Postgres + шесть
служб, это 3–4 ГБ; связка «Postgres + своё приложение + очередь» — то же
самое, только писать её пришлось бы самому.

Что теряется: PocketBase не масштабируется на несколько машин. Для одного
владельца с десятком сотрудников это не ограничение — это запас лет на
пять.

## Установка

```bash
scp server/install-sync.sh root@185.221.199.19:/root/
ssh root@185.221.199.19
bash /root/install-sync.sh
```

Скрипт ставит PocketBase службой, заводит отдельного пользователя (не root),
включает автозапуск и файрвол. Повторный запуск обновляет только сам
PocketBase — данные не трогает.

Проверить: `systemctl status pocketbase`, журнал — `journalctl -u pocketbase -f`.

## Коллекция и правила

Открыть `http://185.221.199.19:8090/_/`, завести администратора (первый вход
попросит сам — **пароль запишите, восстановить его нечем: почта на этом
сервере заблокирована, о чём ниже**).

### 1. Коллекция `wesios_records`

New collection → **Base** → имя `wesios_records`. Поля:

| Поле      | Тип      | Настройки                       |
|-----------|----------|---------------------------------|
| `owner`   | Relation | коллекция `users`, Max select 1, **Required** |
| `coll`    | Plain text | **Required**                  |
| `rid`     | Plain text | **Required**                  |
| `payload` | JSON     | —                               |
| `stamp`   | Plain text | **Required**                  |
| `deleted` | Bool     | —                               |

Почему `stamp` — текст, а не Date: у типа Date в PocketBase свой формат и
своя точность, и приложение сравнивало бы не то, что записало. Строка ISO
переживает круг без изменений, а сравнение времени всё равно делает
приложение.

### 2. Индекс

Вкладка **Indexes** → New index:

```sql
CREATE UNIQUE INDEX idx_wesios_records_unique
  ON wesios_records (owner, coll, rid)
```

Без него два устройства, впервые вышедшие на связь одновременно, создали бы
по копии одной записи, и дальше они бы расходились. С индексом второе
создание получает отказ, а следующий проход синхронизации спокойно
переписывает существующую запись.

### 3. Правила доступа (вкладка API Rules)

Во все пять полей — **одно и то же**:

```
owner = @request.auth.id
```

Это значит: видно и можно менять только своё. Проверку делает сервер, а не
приложение, — клиентская проверка убрала бы чужие записи с экрана, но не
закрыла бы к ним доступ.

### 4. Учётная запись

Collections → `users` → New record: почта и пароль. Это и есть логин, который
вводится в WesiOS.

Регистрация из приложения намеренно не включается: иначе любой, у кого есть
сборка, завёл бы себе учётную запись на вашем сервере.

## Подключение в приложении

Настройки → Данные → **Синхронизация**:

- адрес: `185.221.199.19:8090`
- логин и пароль — те, что завели в `users`
- **Войти** → **Синхронизировать сейчас**

Приложение показывает, на какой именно адрес уйдёт запрос: набранное
`185.221.199.19:8090` превращается в `http://185.221.199.19:8090`. Для голого
IP схема `http`, для домена — `https`.

---

## Когда появится домен

У PocketBase есть встроенный Let's Encrypt — отдельный nginx не нужен и на
одном ядре нежелателен.

1. A-запись домена (например `sync.вашдомен.ru`) → `185.221.199.19`.
2. В `/etc/systemd/system/pocketbase.service` заменить строку `ExecStart`:

```
ExecStart=/opt/pocketbase/pocketbase serve --https=sync.вашдомен.ru --dir=/opt/pocketbase/pb_data
```

3. `systemctl daemon-reload && systemctl restart pocketbase`
4. В приложении сменить адрес на `sync.вашдомен.ru` (без порта — уйдёт по
   `https`).
5. Закрыть 8090: `ufw delete allow 8090/tcp`.

До этого момента пароль уходит на сервер **открытым текстом**. По России до
своего же сервера риск невелик, но затягивать с доменом не стоит.

## Почта

На этом хосте порты 25 / 465 / 587 закрыты провайдером по умолчанию.
Значит, PocketBase не сможет отправлять письма: ни подтверждения, ни сброса
пароля.

Для нашего случая это не мешает — учётные записи заводит владелец в панели,
пароль он же и назначает. Но **пароль администратора восстановить будет
нечем**. Запишите его отдельно.

Если почта понадобится: включить порты в панели хостера либо подключить
внешний SMTP (Яндекс 360, SendGrid) в Settings → Mail.

## Резервные копии

SQLite — один файл. Копия делается копированием:

```bash
cat >/etc/cron.daily/pocketbase-backup <<'SH'
#!/bin/sh
DIR=/opt/pocketbase/backups
mkdir -p "$DIR"
sqlite3 /opt/pocketbase/pb_data/data.db ".backup '$DIR/data-$(date +%F).db'"
find "$DIR" -name 'data-*.db' -mtime +14 -delete
SH
chmod +x /etc/cron.daily/pocketbase-backup
apt-get install -y sqlite3
```

`.backup` вместо `cp` — намеренно: копия работающей базы обычным `cp`
может застать её на середине записи, и восстанавливать будет нечего.

Хранить копии **только** на том же сервере — не резервная копия. Забирайте
их к себе: `scp root@185.221.199.19:/opt/pocketbase/backups/*.db .`

## Что синхронизируется, а что нет

**Уезжает:** счета, операции, задачи, ваши статьи базы знаний, состав
(люди, права, хеши паролей).

**Не уезжает:**

- настройки приложения, тема, язык — они про устройство, а не про данные;
- пароль Wesi Shield и ключи из хранилища — они и существуют затем, чтобы
  лежать на одном устройстве;
- встроенные статьи справки — они приходят с обновлением, а не с сервера.

Хеши паролей сотрудников уезжают намеренно: без них человек, заведённый на
компьютере, не смог бы войти с телефона. Пароль по хешу не восстанавливается.

## Чего пока нет

Сейчас синхронизируются **устройства одной учётной записи**. Владелец видит
свои данные на компьютере и телефоне — и всё.

Общий доступ сотрудников к одним и тем же данным — следующий шаг. Он
требует прав на стороне сервера: правило `owner = @request.auth.id` придётся
заменить на проверку принадлежности к организации, а модуль прав, который
уже есть в приложении, — продублировать в правилах PocketBase. Клиентская
проверка прав, которая там сейчас, скрывает разделы, но не закрывает
данные, — и это честно написано на экране синхронизации.

Второй шаг — переписка. Раскладка уже согласована: рабочие чаты
дополнительно шифруются корпоративным ключом (владелец может прочитать),
личные — только собеседникам. Решение записано в коде,
`lib/features/chats/models/chat_policy.dart`, чтобы не потерялось.
