# Сервер синхронизации WesiOS

Синхронизация устройств: то, что вы завели на компьютере, появляется на
телефоне, и наоборот. Данные лежат на **вашем** сервере — не у Google и не у
меня.

Сервер: Санкт-Петербург, 1 ядро / 2 ГБ / 30 ГБ NVMe, Ubuntu 24.04.

> Везде ниже `АДРЕС` — это IP вашего сервера. Он намеренно не записан в этот
> файл: репозиторий открыт, а «вот мой сервер, вот панель управления на
> порту 8090» — готовая подсказка тому, кто станет его ломать. Сам IP не
> секрет (его видно любым сканером), секрет — связка адреса с тем, что на
> нём стоит.

---

## Пустое правило доступа означает «всем»

Это первое, что нужно знать про PocketBase, и на этом уже один раз
сломалось.

Коллекцию можно завести руками в панели — и тогда пять полей во вкладке
**API Rules** останутся пустыми. Выглядит это как «правила не заданы,
значит закрыто». На деле пустое правило пускает кого угодно, включая
неавторизованных. Сервер при этом работает безупречно: панель открывается,
приложение синхронизируется, в логах чисто. Заметить нечем.

Проверить можно одной командой с любого компьютера — она ходит **без**
пропуска, и правильный ответ здесь 40x, а не 200:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  https://ВАШ-ДОМЕН/api/collections/wesios_records/records
```

Привести права в порядок:

```bash
bash setup-collections.sh --only-rules \
     --admin ПОЧТА --admin-pass ПАРОЛЬ \
     --host https://ВАШ-ДОМЕН
```

`--only-rules` ничего не создаёт и не заводит: только выставляет права и
проверяет их снаружи. Скрипт **падает**, если после правки хоть что-то
осталось открытым, — молчаливого «вроде получилось» здесь быть не должно.

То же самое лежит миграцией в `server/pb_migrations/`: она применяется сама
при запуске PocketBase, поэтому права восстановятся и после переустановки,
и после ручной правки в панели. Скрипт — для «починить сейчас», миграция —
чтобы больше не возвращаться.

Правило `owner = @request.auth.id` означает «запись видит только тот, кто её
положил». Общий доступ сотрудников придёт через поле `org` — оно в схеме с
самого начала.

## Почему PocketBase

На одном ядре и двух гигабайтах выбор невелик. PocketBase — один
исполняемый файл на Go со SQLite внутри: ему хватает 50–80 МБ памяти,
у него есть учётные записи, права на уровне записей, панель управления и
встроенный Let's Encrypt.

Альтернативы отпадают по памяти: своя Supabase — это Postgres + шесть
служб, это 3–4 ГБ; связка «Postgres + своё приложение + очередь» — то же
самое, только писать её пришлось бы самому.

Что теряется: PocketBase не масштабируется на несколько машин. Для одного
владельца с десятком сотрудников это не ограничение — это запас лет на
пять.

## Установка

**Пошаговая инструкция с нуля — [INSTALL.md](INSTALL.md).** Там от «зашёл в
панель хостера» до «синхронизация работает», с расчётом на то, что человек
видит консоль впервые.

Кратко, если консоль не впервые:

```bash
curl -fsSL https://raw.githubusercontent.com/wesiwer/WesiOS/main/server/install-sync.sh -o /root/install-sync.sh
bash /root/install-sync.sh
```

Скрипт ставит PocketBase службой, заводит отдельного пользователя (не root),
включает автозапуск и файрвол. Повторный запуск обновляет только сам
PocketBase — данные не трогает.

Проверить: `systemctl status pocketbase`, журнал — `journalctl -u pocketbase -f`.

## Коллекция и правила — одной командой

```bash
scp server/setup-collections.sh root@АДРЕС:/root/
ssh root@АДРЕС
bash /root/setup-collections.sh \
  --admin вы@почта.ру      --admin-pass ПАРОЛЬ_АДМИНА \
  --user  wesi@почта.ру    --user-pass  ПАРОЛЬ_ДЛЯ_ПРИЛОЖЕНИЯ
```

Скрипт создаёт администратора (если его ещё нет), коллекцию `wesios_records`
с нужными полями, уникальный индекс, правила доступа и учётную запись, под
которой приложение будет входить. Повторный запуск ничего не ломает.

Раньше здесь была страница инструкций «зайдите в панель и создайте шесть
полей». Ошибиться там легко, а ошибка выглядит как «синхронизация молча не
работает» — самый неприятный вид поломки.

**Пароли запишите отдельно.** Почта на этом хосте заблокирована (порты
25/465/587 закрыты провайдером), восстановить их нечем.

Если скрипт остановится — он печатает ответ сервера целиком. Пришлите этот
вывод: по нему видно версию PocketBase и что именно не сошлось.

### Что создаётся и почему так

| Поле | Тип | Зачем |
|---|---|---|
| `owner` | text | Чьи данные. По нему работают все правила |
| `org` | text | Организация. Пока не используется — см. ниже |
| `coll` | text | Какая коллекция: операции, задачи, счета… |
| `rid` | text | Идентификатор записи внутри приложения |
| `payload` | json | Сама запись |
| `stamp` | text | Время правки строкой ISO |
| `deleted` | bool | Надгробие |

Правила сейчас — `owner = @request.auth.id`: видно и можно менять только
своё. Поле `org` заведено пустым **заранее и намеренно**: добавить поле в
коллекцию, где уже лежат данные, — это миграция, а сейчас это ничего не
стоит. Через него пойдёт общий доступ сотрудников, когда до него дойдёт
черёд.

`stamp` — текст, а не Date: у типа Date в PocketBase свой формат и своя
точность, и приложение сравнивало бы не то, что записало. Строка ISO
переживает круг без изменений.

Уникальный индекс по `(owner, coll, rid)` нужен, чтобы два устройства,
впервые вышедшие на связь одновременно, не создали по копии одной записи.

## Подключение в приложении

Настройки → Данные → **Синхронизация**:

- адрес: `АДРЕС:8090`
- логин и пароль — те, что завели в `users`
- **Войти** → **Синхронизировать сейчас**

Приложение показывает, на какой именно адрес уйдёт запрос: набранное
`АДРЕС:8090` превращается в `http://АДРЕС:8090`. Для голого IP схема
`http`, для домена — `https`.

---

## Когда появится домен

У PocketBase есть встроенный Let's Encrypt — отдельный nginx не нужен и на
одном ядре нежелателен.

1. A-запись домена (например `sync.вашдомен.ru`) → `АДРЕС`.
2. В `/etc/systemd/system/pocketbase.service` заменить строку `ExecStart`:

```
ExecStart=/opt/pocketbase/pocketbase serve --https=sync.вашдомен.ru --dir=/opt/pocketbase/pb_data
```

3. `systemctl daemon-reload && systemctl restart pocketbase`
4. В приложении сменить адрес на `sync.вашдомен.ru` (без порта — уйдёт по
   `https`).
5. Закрыть 8090: `ufw delete allow 8090/tcp`.

До этого момента пароль уходит на сервер **открытым текстом**. По России до
своего же сервера риск невелик, но затягивать с доменом не стоит.

## Почта

На этом хосте порты 25 / 465 / 587 закрыты провайдером по умолчанию.
Значит, PocketBase не сможет отправлять письма: ни подтверждения, ни сброса
пароля.

Для нашего случая это не мешает — учётные записи заводит владелец в панели,
пароль он же и назначает. Но **пароль администратора восстановить будет
нечем**. Запишите его отдельно.

Если почта понадобится: включить порты в панели хостера либо подключить
внешний SMTP (Яндекс 360, SendGrid) в Settings → Mail.

## Агент: чтобы видеть нагрузку в приложении

Загрузку процессора, память и диск чужой машины **по сети узнать нельзя** —
сеть про это ничего не сообщает. Либо на сервере что-то эти цифры отдаёт,
либо в приложении их не будет. Рисовать «примерно 45 %» было бы обманом,
поэтому вместо этого — скрипт на двадцать строк.

```bash
scp server/wesios-agent.sh root@АДРЕС:/root/
ssh root@АДРЕС
bash /root/wesios-agent.sh --install
```

Раз в минуту он пишет `/opt/pocketbase/pb_public/wesios-status.json` —
каталог, который PocketBase уже раздаёт как статику. В приложении:
**Ещё → Системный администратор → узел → Адрес агента**:

```
https://АДРЕС/wesios-status.json
```

Проверить, что собирается правильно, не устанавливая:
`bash wesios-agent.sh --print`

**Про доступ.** Этот файл читает любой, у кого есть ссылка: для статики
PocketBase вход не проверяет. Секретного в нём нет — загрузка, память, место
на диске и аптайм, — но это всё же сведения о вашем сервере. Если такое не
устраивает, отдавайте файл через nginx с паролем или ограничьте адрес по IP.

Снять агента: `bash wesios-agent.sh --uninstall`.

Отдельно стоит знать, что в приложении **измеряется само**, без всякого
агента: время ответа, разрешение имени в адрес, срок сертификата и код
ответа сайта. Агент нужен ровно для трёх цифр — процессор, память, диск.

## Резервные копии

SQLite — один файл. Копия делается копированием:

```bash
cat >/etc/cron.daily/pocketbase-backup <<'SH'
#!/bin/sh
DIR=/opt/pocketbase/backups
mkdir -p "$DIR"
sqlite3 /opt/pocketbase/pb_data/data.db ".backup '$DIR/data-$(date +%F).db'"
find "$DIR" -name 'data-*.db' -mtime +14 -delete
SH
chmod +x /etc/cron.daily/pocketbase-backup
apt-get install -y sqlite3
```

`.backup` вместо `cp` — намеренно: копия работающей базы обычным `cp`
может застать её на середине записи, и восстанавливать будет нечего.

Хранить копии **только** на том же сервере — не резервная копия. Забирайте
их к себе: `scp root@АДРЕС:/opt/pocketbase/backups/*.db .`

## Что синхронизируется, а что нет

**Уезжает:** счета, операции, задачи, ваши статьи базы знаний, состав
(люди, права, хеши паролей).

**Не уезжает:**

- настройки приложения, тема, язык — они про устройство, а не про данные;
- пароль Wesi Shield и ключи из хранилища — они и существуют затем, чтобы
  лежать на одном устройстве;
- встроенные статьи справки — они приходят с обновлением, а не с сервера.

Хеши паролей сотрудников уезжают намеренно: без них человек, заведённый на
компьютере, не смог бы войти с телефона. Пароль по хешу не восстанавливается.

## Чего пока нет

Сейчас синхронизируются **устройства одной учётной записи**. Владелец видит
свои данные на компьютере и телефоне — и всё.

Общий доступ сотрудников к одним и тем же данным — следующий шаг. Он
требует прав на стороне сервера: правило `owner = @request.auth.id` придётся
заменить на проверку принадлежности к организации, а модуль прав, который
уже есть в приложении, — продублировать в правилах PocketBase. Клиентская
проверка прав, которая там сейчас, скрывает разделы, но не закрывает
данные, — и это честно написано на экране синхронизации.

Второй шаг — переписка. Раскладка уже согласована: рабочие чаты
дополнительно шифруются корпоративным ключом (владелец может прочитать),
личные — только собеседникам. Решение записано в коде,
`lib/features/chats/models/chat_policy.dart`, чтобы не потерялось.
