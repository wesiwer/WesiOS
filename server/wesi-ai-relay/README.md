# Wesi AI Relay

Зарубежный посредник между основным сервером и провайдером модели.

```
WesiOS → api.wesi-inc.ru → Relay → Gemini → Relay → api.wesi-inc.ru → WesiOS
```

Ключ провайдера живёт **только здесь**. Ни приложение, ни основной сервер
его не видят и видеть не должны.

## Состояние

Relay не развёрнут. Код готов и проверен, чего не хватает — ниже.

## Что нужно, чтобы запустить

Три вещи, и ни одну из них нельзя получить из репозитория:

1. **Зарубежный сервер** с Node 20 или новее и публичным адресом.
2. **Ключ Gemini** (или сервисный аккаунт Vertex). В репозитории его нет.
   Ключ Firebase из `android/app/google-services.json` для этого **не
   годится** — это ключ другого продукта и другого назначения.
3. **Общий секрет** с основным сервером, не короче 32 символов. Сгенерировать:

   ```
   head -c 48 /dev/urandom | base64 | tr -d '/+=' | head -c 48
   ```

## Установка

### Вручную, на самом сервере

```
WESI_MAIN_SHARED_SECRET=... GEMINI_API_KEY=... bash deploy-relay.sh --install
```

Скрипт ставит файлы в `/opt/wesi-ai-relay`, кладёт секреты в
`/etc/wesi-ai-relay.env` с правами 640, заводит пользователя `wesi-relay`
без оболочки и поднимает systemd-службу с урезанными правами. В конце сам
проверяет `/health` и говорит, что осталось.

Relay слушает только localhost. Наружу его выставляет nginx — образец
конфигурации в `nginx-relay.conf`, сертификат через `certbot --nginx`.

### Через GitHub Actions

Workflow `Deploy Wesi AI Relay` (запуск руками). Нужны секреты репозитория:

| Секрет | Зачем |
|---|---|
| `WESI_RELAY_SSH_HOST` | адрес зарубежного сервера |
| `WESI_RELAY_SSH_USER` | пользователь с sudo |
| `WESI_RELAY_SSH_KEY` | приватный ключ |
| `WESI_MAIN_SHARED_SECRET` | общий секрет с основным сервером |
| `GEMINI_API_KEY` | ключ провайдера |
| `WESI_RELAY_SSH_KNOWN_HOSTS` | необязательно, отпечаток сервера |
| `WESI_RELAY_PUBLIC_HOST` | необязательно, для проверки `/health` по HTTPS |

Workflow проверяет наличие всех секретов **до** подключения: иначе
отсутствующий секрет превращается в невнятную ошибку ssh на середине
выкладки.

## Настройка основного сервера

На `api.wesi-inc.ru` создать `/opt/pocketbase/pb_hooks/.wesi-ai-relay.json`
с правами 600:

```json
{
  "url": "https://<адрес-relay>",
  "sharedSecret": "<тот же секрет>",
  "routes": {
    "fast": "google/gemini-2.5-flash",
    "pro": "google/gemini-2.5-pro",
    "maximum": "google/gemini-2.5-pro"
  }
}
```

Секрет обязан совпасть дословно. Расхождение выглядит как 401, а не как
ошибка настройки, и ищется потом долго.

## Подпись запросов

Основной сервер подписывает `requestId + "." + timestamp + "." + body`
ключом общего секрета, Relay проверяет ту же строку и запоминает
идентификатор.

Обе половины обязательны и обе меняются только вместе:

- **идентификатор в подписи** привязывает подпись к конкретному запросу.
  Пока он был вне подписи, перехваченный запрос отправлялся повторно с
  любым другим идентификатором, и подпись сходилась;
- **память об идентификаторах** не даёт использовать один дважды. Проверка
  времени этого не делает — она пропускает всё моложе пяти минут.

Память проверяется только для подлинных запросов: иначе подделкой можно
было бы занять чужой идентификатор заранее и не дать пройти настоящему.
Переполнение памяти — отказ, а не пропуск: отклонённый настоящий запрос
несравнимо дешевле принятого повтора.

Строка подписи проверяется тестом с обеих сторон (`relay.test.mjs`) — менять
одну сторону нельзя, это даёт не «менее безопасно», а полностью неработающий
Wesi AI.

## Проверка без провайдера

Полный путь подписи проверяется локально, без зарубежного сервера и без
настоящего ключа:

```
WESI_MAIN_SHARED_SECRET=test_secret_for_local_roundtrip_only_48chars \
  WESI_RELAY_PORT=8799 GEMINI_API_KEY=fake node server.mjs
```

Подписанный запрос при этом доходит до самого провайдера и отвергается
только ключом — ответ `502 WAI_PROVIDER_REJECTED`. Это и есть признак того,
что вся цепочка проверки подписи работает; повтор того же запроса вернёт
`401 WAI_RELAY_REPLAY_DETECTED`.
